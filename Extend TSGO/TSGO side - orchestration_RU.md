> > Каталог исходников: `internal/execute/build` — соответствует режиму сборки tsgo `--build/-b` (Project References, ссылки на проекты), это Go-переписанная версия `tsc --build`; специально предназначен для оркестрации нескольких подпроектов monorepo: топология зависимостей, инкрементальность, параллельное планирование.
> > Оркестрация tsgo monorepo **полностью основана на `references` из tsconfig**, не читает workspace из package.json и отделена от систем оркестрации pnpm/turborepo.

## Обязанности файлов каталога (internal/execute/build)

|Файл|Ключевая обязанность|
|---|---|
|`builder.go`|Главная точка входа билдера; разбор графа проектов, топологическая сортировка, планирование задач, определение инкрементального состояния|
|`project_graph.go`|Построение графа зависимостей проектов: сканирует все references из tsconfig, строит ориентированный граф, обнаруживает циклические зависимости|
|`incremental.go`|Чтение/запись инкрементального состояния `.tsbuildinfo`; сравнение отпечатков файлов, определение необходимости перекомпиляции подпроекта|
|`worker.go`|Пул воркеров на goroutine Go; параметр `--builders=N` управляет количеством параллельно собираемых подпроектов|
|`diagnostics.go`|Агрегация ошибок компиляции нескольких подпроектов, распространение ошибок|

## Общий процесс оркестрации

### Ключевое различие двух групп параметров параллелизма tsgo

1. `--builders N`: **параллелизм уровня проектов monorepo** — управляет количеством одновременно собираемых разных подпроектов tsconfig, соответствует пулу воркеров `internal/execute/build`, это уровень оркестрации;
2. `--checkers N`: **параллелизм уровня файлов внутри одного проекта** — внутри одного подпроекта несколько исходных файлов проверяются на типы параллельно, относится к уровню compiler/checker и не входит в логику оркестрации monorepo.

> Комбинированный эффект: `--builders 4 --checkers 4` — одновременно максимум 4 подпроекта, внутри каждого подпроекта максимум 4 файла проверяются параллельно; теоретический максимум — 16 задач checker.

## 1. Построение графа зависимостей проектов ProjectGraph (project_graph.go)

### Вход

`references[]` корневого tsconfig, каждый элемент `{path: "../packages/xxx"}`; подпроект обязан иметь `composite:true` (то же ограничение, что в оригинальном tsc).

### Шаги обработки

1. Рекурсивно разобрать каждый путь ссылки, прочитать tsconfig подпроекта; внутри подпроекта снова могут быть references — весь граф разворачивается рекурсивно;
2. Создать узлы: каждый узел представляет один composite-проект tsconfig;
3. Создать рёбра: A references B → A **зависит от B**; B должен быть собран до сборки A;
4. **Обнаружение циклических зависимостей**: если в графе найден цикл — сразу выбрасывается диагностика, сборка прерывается; циклические ссылки между подпакетами monorepo недопустимы;
5. На выходе — DAG (направленный ациклический граф).

> ⚠️ Внимание: **package.json dependencies/workspace не читается**. Зависимости берутся только из tsconfig references, не из npm/pnpm workspace. Даже если в package.json записан `workspace:*`, tsgo-build этого не увидит — зависимости нужно вручную объявлять через tsconfig references.

## 2. Топологическая сортировка и порядок сборки (builder.go)

После получения DAG выполняется топологическая сортировка:

- Первыми идут узлы со входной степенью 0 (не зависящие от других проектов);
- Узел допускается в пул воркеров только после **завершения сборки всех проектов, от которых он зависит**;
- Несколько проектов одного уровня (не зависящих друг от друга) могут собираться параллельно, максимальный параллелизм ограничен `--builders`.

Пример: зависимости monorepo

```
app → utils
app → ui
ui → utils
```

Порядок топологического выполнения:

1. Сначала собирается utils (зависимостей нет)
2. После завершения utils параллельно собираются ui и app (ui зависит от utils; app зависит от utils/ui)

## 3. Инкрементальная сборка (incremental.go)

В выходном каталоге каждого composite-проекта генерируется `.tsbuildinfo`, хранящий:

- Отпечатки (hash) всех исходных файлов и файлов входных проектов-зависимостей;
- Снимок опций компиляции прошлого запуска.

Для каждого проекта в графе:

1. `.tsbuildinfo` не существует → нужна сборка;
2. Изменились опции компиляции tsconfig → нужна сборка;
3. Изменились исходные файлы проекта → нужна сборка;
4. **Любой подпроект, от которого зависит данный проект, был пересобран** → текущий проект обязан пересобраться (транзитивная инвалидация);
5. Все отпечатки совпали → компиляция пропускается.

> Главное: транзитивная инвалидация. A ссылается на B, B пересобран — тогда A обязан перекомпилироваться, даже если его собственные файлы не менялись, ради согласованности ссылок на типы. Это ключевая логика оркестрации monorepo.

## 4. Планирование пулом воркеров (worker.go)

- Параметр `--builders` задаёт количество воркеров, по умолчанию выводится из числа ядер CPU;
- Пул реализован на goroutine Go; очередь задач хранит ожидающие сборки узлы проектов;
- Ограничение: проект не планируется, пока не завершены все его предшествующие зависимости;
- Каждый воркер получает задачу проекта и выполняет полную компиляцию этого подпроекта (проверка типов + emit);
- Ошибки компиляции подпроекта: записываются в диагностику; в зависимости от continueOnError можно либо прервать всю сборку, либо продолжить сборку остальных несвязанных проектов.

> Сравнение с оригинальным Node-tsc --build: оригинал однопоточный и последовательный, tsgo за счёт goroutine реализует настоящий параллелизм на уровне проектов — это крупнейший прирост производительности tsgo monorepo.

## 5. Агрегация диагностики и код выхода (diagnostics.go)

- Собираются все error/warning от компиляции каждого подпроекта;
- После завершения всех задач все диагностики печатаются единым списком с указанием, из какого подпроекта каждая ошибка;
- При наличии ошибок процесс возвращает ненулевой код выхода — в CI падение распознаётся корректно.

## 6. Сравнение с традиционными инструментами (в разрезе оркестрации monorepo)

|Инструмент|Источник зависимостей|Гранулярность планирования|Параллелизм|Источник инкрементальности|
|---|---|---|---|---|
|tsgo -b|tsconfig references|проект tsconfig|параллелизм уровня проектов (--builders) + параллелизм файлов внутри проекта (--checkers)|.tsbuildinfo, транзитивная инвалидация по отпечаткам файлов|
|оригинальный tsc -b|tsconfig references|проект tsconfig|однопоточный, последовательный|.tsbuildinfo|
|turborepo/nx|package.json dependsOn|npm-пакет|параллелизм уровня процессов|собственный hash кэша|
|pnpm -r run build|package.json dependencies|npm-пакет|уровень процессов, топологический|нативной ts-инкрементальности нет|

> Важные различия:
>
> 1. Слой оркестрации tsgo признаёт только tsconfig references, **package.json не читает**;
> 2. tsgo — встроенная в компилятор оркестрация, внешние инструменты не нужны; возможна инкрементальность на уровне компиляции; turborepo — внешний планировщик процессов, способен только кэшировать вывод целого процесса.

## 7. Типичный пример использования monorepo

Структура каталогов

```
monorepo/
├─ tsconfig.json (root solution, references указывают на packages/*)
└─ packages/
   ├─ utils/tsconfig.json composite:true
   ├─ ui/tsconfig.json composite:true references:["../utils"]
   └─ app/tsconfig.json composite:true references:["../utils","../ui"]
```

Команда запуска:

```bash
# полная сборка monorepo: 4 параллельных проекта, внутри каждого 4 параллельных checker
tsgo -b --builders 4 --checkers 4
```

## 8. Ограничения и подводные камни

1. Каждый подпакет обязан иметь `composite:true`, иначе references не действует;
2. Циклические ссылки между подпакетами сразу дают ошибку;
3. references нужно писать вручную, workspace-зависимости из package.json автоматически не читаются;
4. `.tsbuildinfo` — ядро инкрементальности, удаление файла принудительно вызывает полную пересборку;
5. В режиме watch внутренняя логика оркестрации build переиспользует тот же ProjectGraph: инкрементальное отслеживание изменений файлов триггерит частичную пересборку.
