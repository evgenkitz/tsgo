# [ArkTS][Файлы деклараций] Генерация файлов деклараций ArkTS и нормализованная раскладка вывода библиотеки

> Требование: поддержать генерацию деклараций `.d.ets` (включая объявления аннотаций с сохранением значений по умолчанию у их свойств) и записывать вывод библиотеки на диск по согласованной раскладке.
>
> Документ описывает предысторию и объём поставки по этому требованию. Эталонные реализации закреплены на `ace_ets2bundle` @ `5b89da97cc91695b9623e1d76afb6e2a0859ec3d` и OH TSC (ohos-typescript, подключён здесь как `_submodules/third_party_typescript`) @ `f2a0cebe8c` (4.9.5-r4); для сравнения используется оригинальный TypeScript `_submodules/TypeScript` @ `c3bd12d88`. При смене версий все ссылки придётся искать заново.
>
> Далее «эталон» и «существующая цепочка инструментов» означают цепочку компиляции ArkTS, которая поставляется в SDK сегодня, то есть ets-loader (`ace_ets2bundle`), управляющий OH TSC. Это требование заменяет и то и другое.
>
> Все ссылки даются как «файл + функция», без номеров строк — номера строк расходятся между версиями, имена функций нет. Документ самодостаточен и не зависит от других документов. Черновик от 2026-09-22.

## 0. Термины

Эти термины встречаются ниже постоянно; вот они простыми словами, чтобы не приходилось догадываться по ходу чтения.

| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Файл деклараций                      | Файл, в котором только типы и нет реализации. `.ts` даёт `.d.ts`, `.ets` даёт `.d.ets`. При компиляции потребитель читает только его, исходник — никогда                                                                        |
| Генерация деклараций                 | Процесс, которым компилятор урезает исходный файл до файла деклараций: выбрасывает тела функций, выбрасывает закрытые члены, выписывает выведенные типы явно                                                                    |
| Аннотация                            | Объявление `@interface Foo { ... }` в ArkTS и его использование в другом месте как `@Foo(...)`. Это другой механизм, не декораторы TypeScript; они лишь выглядят похоже                                                         |
| Свойство аннотации                   | Поля внутри тела объявления аннотации, например `a` в `@interface Anno { a: number = 1 }`. Они **обязаны** попадать в файл деклараций вместе со значениями по умолчанию                                                         |
| `illegalDecorators`                  | Внутреннее поле TypeScript, куда попадают декораторы на узлах, которым по синтаксису декораторы не положены, но они там есть. Аннотации ArkTS и `@Sendable` попадают именно сюда                                                |
| Список разрешённых декораторов       | Опция компилятора `ets.emitDecorators`. По умолчанию файл деклараций выбрасывает все декораторы; остаются только имена из этого списка                                                                                          |
| Пространство имён с `declare`        | `declare namespace X { ... }` в файле деклараций. Его члены экспортируются неявно, поэтому модификаторы `export` нужно снимать                                                                                                  |

| `singleFileEmit`                     | Переключатель режима конвейера, который передаёт вниз система сборки. Он выбирает между «генерировать по файлу» и «генерировать пачкой на `buildEnd`», **и он же решает, через какую точку записи декларации попадают на диск** |
| Запись на диск                       | В какой каталог и по какому относительному пути компилятор пишет вывод. В этом требовании это не «просто вызвать `WriteFile`», а набор правил ветвления                                                                         |
| Запись о выводе                      | `harFilesRecord` в эталоне: таблица «исходный файл → пути каждого полученного из него вывода». Её читают объединение деклараций, обфускация и финальная запись                                                                  |
| `etsFortgz`                          | Корневой каталог для деклараций HAR с байт-кодом и общих HSP, расположен по пути `<каталог сборки модуля>/../etsFortgz`                                                                                                         |
| `oh-exports`                         | Поле в манифесте пакета `oh-package.json5`, которое объявляет, какие файлы пакет разрешает экспортировать                                                                                                                       |

| Сопутствующий файл                   | Побочный продукт объединения деклараций, `<имя входа>-declarations.d.ts` / `.d.ets`: в него попадает та половина деклараций, которая пересекает границу расширений                                                              |

## 1. Предыстория

### 1.1 Для публикации библиотеки нужны две вещи, и ни одной из них в tsgo сегодня нет

В приёмочном базовом проекте `sample_in_harmonyos` 12 модулей: 8 — библиотеки (`common` и 7 функциональных) и 4 — входные HAP. Чтобы библиотекой могли пользоваться другие модули, она должна поставлять поверхность типов, а эта поверхность — `.d.ets`. Чтобы до неё дойти, нужно сразу два условия: компилятор должен правильно урезать `.ets` до `.d.ets`, и эти `.d.ets` вместе с остальным выводом должны оказаться там, где потребитель их найдёт. Если сделать только первое, библиотека всё равно останется непубликуемой — поэтому оба условия живут в одном требовании.

Сегодня в tsgo не выполнено ни то, ни другое, но в очень разной степени.

**Что касается генерации деклараций, в tsgo есть полная реализация из оригинального TypeScript; не хватает слоя ArkTS.** Четыре файла в `internal/transformers/declarations/` (`transform.go`, `util.go`, `diagnostics.go`, `tracker.go`) — это полный перенос генерации деклараций из оригинального TypeScript, и соответствие расширений `.ets → .d.ets` уже реализовано (`GetDeclarationEmitExtensionForPath` и `GetPossibleOriginalInputExtensionForExtension` в `internal/tspath/extension.go`). Но во всех этих четырёх файлах **ноль** упоминаний ArkTS: ни объявлений аннотаций, ни свойств аннотаций, ни списка разрешённых декораторов, ни `@Sendable`, ни снятия `export` внутри пространств имён с `declare`. На стороне эталона соответствующие правки сосредоточены в `transformers/declarations.ts` и вспомогательном файле `ohApi.ts`, ещё три — в `checker.ts` и `transformers/declarations/diagnostics.ts`. Все точки правок перечислены в таблице в 1.8, и у каждой указан пункт поставки из этого документа, который за неё отвечает.

**Что касается записи на диск, в tsgo нет даже соответствующего слоя.** В tsgo есть стандартные опции `outDir` / `declarationDir`, которые выражают «перенести всё дерево в другой каталог от одной базы». У правил эталона не такая форма: набор вывода зависит от формы модуля, базовый каталог выбирается из трёх вариантов, файлы под `oh_modules` исключаются целиком, а в некоторых конвейерах путь одного и того же файла вычисляется дважды от двух разных баз, после чего файлы копируются попарно. В эталоне весь этот слой живёт в ets-loader, а не в компиляторе.

### 1.2 Эталон делит это на три части

```
   hvigor передаёт вниз projectConfig (moduleType / byteCodeHar / useTsHar / singleFileEmit / bundledDeclare / directories …)
        │
        ▼
   ets-loader (ace_ets2bundle)
     · processHarSourceFiles()      обходит «разрешённые модули ∪ корневые файлы» и решает по каждому файлу: скопировать как есть или сгенерировать заново
     · generateSourceFilesInHar()   выбирает один из трёх путей публикации, вычисляет место назначения, регистрирует его в harFilesRecord
     · writeDeclarationFiles() / mangleDeclarationFileName()   две взаимоисключающие точки записи, выбор зависит от singleFileEmit
     · performDeclarationMerging()  условно запускаемое объединение деклараций, строит собственную вторую Program
        │
        │  program.emit(sourceFile, writeFile, /*emitOnlyDtsFiles*/ true, …)
        ▼
   OH TSC (ohos-typescript)
     · transformers/declarations.ts   аннотации, сохранение декораторов, отсечение по видимости, пространства имён с declare
     · ohApi.ts                        движок списка разрешённых emitDecorators, контекст @Styles, проверка @Sendable
     · checker.ts                      вывод типов и вычисление констант для свойств аннотаций (входные данные генерации деклараций)
```

**Первая часть — генерация деклараций внутри компилятора.** Это перенос функция за функцией с понятной поверхностью правок и готовыми эталонными выводами для проверки; самая безопасная часть.

**Вторая часть — запись на диск и учёт в ets-loader.** В tsgo такого слоя нет, поэтому сначала нужно решить, куда он встраивается и какие входные данные передаёт вниз система сборки, и только потом говорить о том, как его писать.

**Третья часть — объединение деклараций.** Оно запускается условно и оценивается отдельно: `declaration_merger.ts` 1998 строк + `declaration_merger_utils.ts` 559 строк + `declaration_merger_sysapi.ts` 375 строк, всего около 2932 строк, плюс 117 тестовых примеров. Сейчас оно вынесено за рамки требования, но то, когда оно срабатывает, раньше описывали неверно; см. 1.7.

Оценивать эти три части вместе нельзя.

### 1.3 В файлах деклараций правила для аннотаций прямо противоположны обычным свойствам

Это самая трудоёмкая часть всего требования и та, где труднее всего угадать правильное поведение.

Когда обычное свойство класса попадает в файл деклараций, его инициализатор всегда отбрасывается — именно это делает `ensureNoInitializer` в `declarations.ts`. Со свойствами аннотаций всё наоборот: инициализатор **обязан** остаться в файле деклараций дословно, потому что потребитель опирается на него при компиляции, чтобы знать, «какое значение это свойство аннотации принимает по умолчанию, если его не написали». Вдобавок у свойств без явно указанного типа тип нужно вывести из значения по умолчанию и подставить.

В эталоне это, соответственно, одна строка и одна ветка. Сохранение инициализатора — в `visitDeclarationSubtree` в `declarations.ts`, где ветка `AnnotationPropertyDeclaration` передаёт `input.initializer` напрямую в `factory.updateAnnotationPropertyDeclaration`; вывод типа — в `ensureType` в том же файле, где на ветке `AnnotationPropertyDeclaration` сначала пробуется `createTypeOfDeclaration`, а если не вышло — берётся `createTypeOfExpression(node.initializer, …)`.

Вот как выглядит готовый вывод (пример `tests/cases/conformance/annotations/annotationDeclarationFieldInitializer1.ets`, ожидаемый вывод — раздел `.d.ets` в `tests/baselines/reference/annotationDeclarationFieldInitializer1.js`):

```ets
// исходник
@interface Anno {
    a: number = +1
    d  = !1
    z = 1 == 1
}

// .d.ets
declare @interface Anno {
    a: number = +1;
    d: boolean = !1;
    z: boolean = 1 == 1;
}

// .js — пусто; объявление аннотации из вывода скрипта стирается целиком
```

Картина полна, только когда сходятся все три вещи: инициализаторы сохранены дословно, у `d` и `z` без типа из значений по умолчанию выведен `boolean`, а на стороне `.js` пусто. Третье в требование не входит (то, как аннотации стираются из вывода скриптов, — отдельное направление работ), но оно объясняет, почему сторона деклараций обязана сохранять инициализаторы: среда выполнения объявлений аннотаций не видит, поэтому значения по умолчанию могут дойти до потребителя только через файл деклараций.

**Выражения переносятся дословно, а не вычисляются и затем печатаются.** Посмотрите на вывод `annotationDeclarationFieldInitializer8`: `c: Array<Array<number>> = [[1 + a * b / 3], [E.A + b], [a + E.A], []];` — скобки, операторы и ссылки на идентификаторы сохраняют исходную форму. В проверке типов есть вычислитель констант (`evaluateAnnotationPropertyConstantExpression` в `checker.ts`), но его результат идёт через `getAnnotationPropertyEvaluatedInitializer` в `EmitResolver`, и потребитель у него — цепочка вывода скриптов в `ohApi.ts`, а **не** генерация деклараций. Генерации деклараций нужен исходный узел AST.

**Генерация выполняется даже при неудачном вычислении.** В примере `annotationDeclarationFieldInitializerError1` все три свойства сообщают TS28034 (`Default value of annotation property can be a constant expression, got: '{0}'.`), но в `.d.ets` всё равно дословно пишутся `a: number = A;`, `b: number = B();`, `c: number = C;`. Диагностики не блокируют генерацию; это поведение нужно повторить и не добавлять своих проверок.

Рядом с этим — две диагностики со стороны проверки типов, обе выдаются в `checkAnnotationPropertyDeclaration` в `checker.ts`: TS28033 (тип свойства аннотации может быть только number / boolean / string / const enum или массивом из них) и TS28034. Есть и особый случай: для свойства типа `const enum` без значения по умолчанию `addAnnotationPropertyEnumInitalizer` в том же файле синтезирует инициализатор вида `new Number(0) as number` и кладёт его в `NodeLinks` — комментарий эталона называет его «бесполезным выражением, запрещённым для пользователей»; оно служит тому, чтобы дальше по цепочке шла информация о числовом типе члена перечисления. Это тоже идёт только через цепочку вывода скриптов.

### 1.4 Сохранение декораторов: сегодня в tsgo это просто неверно, и это видно без аннотаций и структур

По умолчанию файл деклараций выбрасывает все декораторы. С ArkTS так нельзя — `@Component`, `@State`, `@Styles` и подобные должны оставаться в `.d.ets`, иначе поверхность типов, которую получает потребитель, неполна. Эталон использует движок со списком разрешённых: `getEffectiveDecorators` в `ohApi.ts` читает `ets.emitDecorators`, оставляет только перечисленные в настройке имена, а для записей с `emitParameters: false` ещё и сокращает `@Consume("1")` до `@Consume`. Если опция не настроена, выбрасывается всё.

Сегодня tsgo безусловно выполняет `core.Filter(mods.Nodes, ast.IsModifier)` в `ensureModifiers` в `internal/transformers/declarations/transform.go`, отсекая все декораторы. Сама опция разбирается нормально (`EtsOptions.EmitDecorators` в `internal/core/arkts.go`, `ParseEtsOptions` и `parseEtsEmitDecoratorsOptions` в `internal/tsoptions/arkts.go`), но кроме собственных модульных тестов у неё **нет ни одного потребителя**.

Это проверено: при `ets.emitDecorators = [Observed, State, Styles]` и входе `@Observed export class Model { @State value: string = "a" }` tsgo выдаёт `export declare class Model { value: string; }`, оба декоратора теряются.

**Этот кусок стоит выделить отдельно: он срабатывает гораздо шире остальных пунктов.** Пункты про аннотации ждут, пока проверка типов научится понимать аннотации, пункты про структуры ждут преобразования структур из направления ArkUI; а этому не нужно ни то, ни другое — обычные `class` или `function`, написанные в файле `.ets`, уже его задевают. В эталоне его подкрепляют 12 готовых эталонных выводов (см. 5, «Приёмка»).

В ту же группу со схожим механизмом входят ещё два пункта. Первый — `inEtsStylesContext` в `ohApi.ts`: методы и функции с декоратором `@Styles` в `.d.ets` не несут параметров типа; используется в `visitDeclarationSubtree` и `transformTopLevelDeclaration` в `declarations.ts`. Второй — `stripExportModifiersForEts` в `declarations.ts`: он снимает модификаторы `export` внутри пространств имён с `declare`, сохраняя при этом декораторы и аннотации ETS. В оригинальном TypeScript есть только вариант, который декораторы не сохраняет, — и в tsgo тоже. В эталонных выводах есть наглядный пример того, что дают оба вместе (`functionAndClassWithDecorator.d.ets`):

```ets
declare namespace ns {
    class A {
        a: number;
    }
    function F(): void;
    @Styles
    function globalFancy();
    @Styles
    function globalFancy2();
}
```

В исходнике все четыре члена написаны с `export`; в выводе `export` исчезли, а `@Styles` остался, причём у `globalFancy` нет даже типа возвращаемого значения.

### 1.5 Какие файлы библиотека вообще обязана произвести

Первый вопрос для половины про запись на диск — не «куда», а «что». В эталоне это решает форма модуля: ветвление в `generateModuleAbc` в `generate_module_abc.ts` (хук `buildEnd` у rollup). Когда выполняется `compileHar && !byteCodeHar`, там запускается только `SourceMapGenerator.buildModuleSourceMapInfo`, а затем идёт **`return`**, пропускающий всю `generateAbc`; все остальные формы проходят полную генерацию abc.

| Форма модуля | Набор вывода |
|---|---|
| HAR с исходниками (`compileHar && !byteCodeHar`) | Вывод исходников (`.js`, или `.ts` при включённом `useTsHar`) + `.d.ets` / `.d.ts` + sourcemap (карта исходников), **без abc** |
| HAR с байт-кодом (`compileHar && byteCodeHar`) | `modules.abc` + `.d.ets` / `.d.ts` + sourcemap |
| Общий HSP (`compileShared`) | Как у HAR с байт-кодом, но относительная база берётся от корня проекта |
| HAP | abc + sourcemap, **без деклараций** (`processHarSourceFiles` вызывается только при `compileHar \|\| compileShared`) |

**`useTsHar` — первая развилка в этой таблице: он решает, что выдаёт HAR с исходниками, `.js` или `.ts`.** Расширение выбирается в `setIncrementalFileInHar` в `fast_build/ets_ui/rollup-plugin-ets-typescript.ts` (`useTsHar ? '.ts' : '.js'`), и та же функция регистрирует в `allFilesInHar` соответствие «кэш → сборка» и для деклараций, и для вывода исходников. Кроме того, его читают ещё в двух местах на стороне сборки: `getOrCreateLanguageService` в `ets_checker.ts` при `compileHar && !byteCodeHar` смотрит, изменился ли он, как на условие сброса всего кэша (`useTsHarDiff`; изменение отбрасывает кэш целиком); `process_ui_syntax.ts` выдаёт предупреждение, встретив класс с `@Sendable` в JS-HAR (`compileHar && !useTsHar`).

**То, как получается текст вывода исходников, в требование не входит; входят их расширение и место назначения.** Иначе говоря, как возникает текст `.js` / `.ts`, здесь не обсуждается, а «должен ли этот модуль выдать `.js` или `.ts` и в какой каталог он попадёт» — обсуждается.

### 1.6 Куда попадают эти файлы: три пути публикации, одна таблица записей, две точки записи

**Точка сбора — `processHarSourceFiles` в `ets_checker.ts`**, её вызывает `processBuildHap` в том же файле при `compileHar || compileShared`. Она обходит «множество разрешённых модулей ∪ множество корневых файлов» и делает с каждым файлом одно из двух:

- если это уже `.d.ets` / `.d.ts` — **прочитать файл целиком и скопировать как есть**;
- если это `.ets` / `.ts` — сгенерировать его отдельно вызовом `program.emit(sourceFile, writeFile, undefined, /*emitOnlyDtsFiles*/ true, undefined, true, true)`, забрать текст и записать как `.d` + исходное расширение.

**Последние два из этих семи аргументов стоит отметить отдельно.** OH расширил сигнатуру `Program.emit` до `(sourceFile, writeFileCallback, cancellationToken, emitOnlyDtsFiles, transformers, forceDtsEmit, skipDiagnostics)`; последний, `skipDiagnostics`, добавлен в OH, оригинальный TypeScript заканчивается на `forceDtsEmit`. `forceDtsEmit: true` заставляет `emitWorker` в `program.ts` пропустить `handleNoEmitOptions` — **декларации производятся даже при наличии ошибок**; `skipDiagnostics: true` позволяет генерации проставить обратные ссылки аннотаций, не запуская проверку типов. Если скопировать этот вызов, не разобравшись в этих двух аргументах, потеряется поведение «производить даже при ошибке».

Нужно повторить два фильтра: при сборке HAR всё, в чьём пути встречается имя каталога пакетов (`oh_modules`), пропускается целиком; `.ets` / `.ts` под `/oh_modules/` тоже пропускаются. Оба фильтра перестают действовать при включённом `bundledDeclare` — с этим переключателем декларации под `oh_modules` тоже нужно выносить. И ещё одно, более важное: **всё тело цикла обёрнуто в `try { … } catch (err) {}`, поэтому исключения проглатываются без записи в журнал**. Так устроен эталон; это надо повторить как есть и не превращать в ошибку.

**Путь на самом деле определяет `generateSourceFilesInHar` в `utils.ts`**: она складывает путь назначения из трёх вещей — относительной базы, корня вывода и переключателя `buildInHar`, — и три пути публикации суть три их сочетания:

| Форма модуля | Относительная база | Корень вывода | `buildInHar` |
|---|---|---|---|
| Общий HSP (`compileShared`) | Корень проекта `projectRootPath` | `<каталог сборки модуля>/../etsFortgz` | true |
| HAR с байт-кодом (`byteCodeHar`) | Корень модуля `moduleRootPath` | `<каталог сборки модуля>/../etsFortgz` | false |
| HAR с исходниками | Корень модуля `moduleRootPath` | `cachePath` | false |

`buildInHar` — больше чем логическое значение: в `genTemporaryPath` в `utils.ts` он управляет сразу двумя вещами — сохраняет ли относительный путь префикс с именем модуля и появляется ли в пути вывода уровень каталога `TEMPORARY`. Когда выполняются оба условия, `compileHar && buildInHar`, префикс с именем модуля стирается в пустую строку (`moduleA/src/main/ets/test.js` → `src/main/ets/test.js`) — так выглядит относительный путь внутри пакета HAR.

**Запись на диск означает ещё и регистрацию записи о выводе.** `harFilesRecord` в `utils.ts` — таблица «путь исходного файла → `GeneratedFileInHar`» с шестью полями: `sourcePath`, `sourceCachePath`, `obfuscatedSourceCachePath`, `originalDeclarationCachePath`, `originalDeclarationContent`, `obfuscatedDeclarationCachePath`. Два вида вывода регистрируются в двух разных местах:

- **Декларации** регистрирует `generateSourceFilesInHar`, и **по умолчанию они только регистрируются, но не пишутся** — `originalDeclarationContent` остаётся в памяти; запись происходит один раз при регистрации и только при включённом `bundledDeclare`.
- **Вывод исходников** регистрирует `writeObfuscatedSourceCode` в `ark_utils.ts`: если `moduleInfo.originSourceFilePath` непуст, она записывает `buildFilePath` в `sourceCachePath`, а затем пишет файл напрямую через `writeFileSyncCaseAware`. Живой конвейер на rollup идёт этим путём, а не через `generateSourceFilesInHar` — два её места вызова для `.js` в `process_har_writejs.ts` и `result_process.ts` остались со времён webpack и больше не выполняются.

**У вывода деклараций две взаимоисключающие точки записи, и выбирает между ними `singleFileEmit`. Это легче всего упустить.**

- `singleFileEmit` включён: обработчик `beforeBuildEnd` в `rollup-plugin-gen-abc.ts` (`order: 'pre'`) вызывает `writeDeclarationFiles` в `ark_utils.ts`, та обходит `harFilesRecord`, записывая `originalDeclarationContent` в `originalDeclarationCachePath`, после чего делает `return`, пропуская все последующие ветки того же обработчика.
- `singleFileEmit` выключен: путь идёт через `handlePostObfuscationTasks` в `ob_config_resolver.ts` → `mangleDeclarationFileName` в `ark_utils.ts`, условие входа — `compileToolIsRollUp() && compileMode === ESMODULE`, **независимо от того, включена ли обфускация**; она так же обходит `harFilesRecord`, вызывая для каждой записи `writeObfuscatedSourceCode`, и при выключенной обфускации эта функция доходит до финального `writeFileSyncCaseAware` и записывает файл.

Нужно покрыть обе точки, иначе декларации перестанут записываться, как только сменится режим конвейера. Замечание об одной неточности в самом эталоне: комментарий к `writeDeclarationFiles` утверждает «Writes declaration files in debug mode», что не совпадает с настоящим условием (`singleFileEmit`); не переносите поведение по этому комментарию.

**Этому слою нужны девять входных данных, согласованных с системой сборки.** Требование зависит от всех; без любого из них слой не вычислит места назначения:

| Вход | Смысл | Что соответствует в эталоне |
|---|---|---|
| `moduleType` | `entry` / `feature` / `har` / `shared`; решает набор вывода и то, какой путь берётся | Заменяет два логических значения `compileHar` + `compileShared` |
| `byteCodeHar` | Собирается ли этот модуль как HAR с байт-кодом | `projectConfig.byteCodeHar` |
| `useTsHar` | Остаётся ли вывод HAR с исходниками в `.ts` или превращается в `.js` | `projectConfig.useTsHar` |
| `singleFileEmit` | Режим конвейера; он же решает, какой точкой записи пользуются декларации | `projectConfig.singleFileEmit` |
| `emitDeclarations` | Нужно ли производить декларации | Выводится из `compileHar` / `compileShared` |
| `declarationOutDir` | Корневой каталог вывода деклараций | `declaredFilesPath` или `<каталог сборки модуля>/../etsFortgz` |
| `harOutDir` | Каталог loader_out этого HAR | `aceModuleBuild` / `buildPath` |
| `bundledDeclare` | Переключатель объединения деклараций | `projectArkOption.bundle.bundledDeclare` |
| `declarationEntryFiles` | Набор входных файлов для объединения деклараций | Вычисляется из `oh-exports` или поля `main` в манифесте |

**`harOutDir` нельзя свести к стандартному `outDir`.** В конвейере `compileHar && !byteCodeHar` обе базы, cachePath и buildPath, **живут в одном прогоне одновременно**: путь одного и того же файла вычисляется один раз от кэша и один раз от каталога сборки (во втором вызове дополнительно передаётся `buildInHar`, поэтому правила относительного пути другие), после чего файлы копируются попарно — таблица `incrementalFileInHar` в `handleFinishModules` в `compile_info.ts` и есть это соответствие «кэш → сборка». Либо повторяем эту форму, либо явно решаем, что «копирование из кэша в loader_out — забота системы сборки», и записываем правила на её стороне; см. 4.

### 1.7 Условие запуска объединения деклараций дважды называли неверно

Это условие раньше называли неверно дважды: сначала как «проект подключает HAR с байт-кодом или общий HSP», потом как `bundledDeclare && (byteCodeHar || compileShared)`. **Неверно и то и другое.** Единственное жёсткое условие — в `serviceChecker` в `ets_checker.ts`, и смотрит оно на один переключатель, `projectArkOption.bundle.bundledDeclare`; следующее за ним `byteCodeHar || compileShared` решает только, что взять каталогом входных данных для объединения — `declaredFilesPath` или `cachePath/<moduleName>`, — и каким будет значение аргумента `isByteCodeHar`, но **не решает, запускать ли его вообще**; эта ветка `else` существует как раз для HAR с исходниками и HAP.

Верная формулировка: **для любого модуля, сборку которого мы берём на себя (HAP / HSP / HAR с исходниками / HAR с байт-кодом), объединение деклараций запускается, если включён `arkOptions.bundle.bundledDeclare`.** Быть HAR с байт-кодом тут ни при чём: HAR с байт-кодом с выключенным переключателем его не запускает, HAR с исходниками с включённым — запускает, и вдобавок перезаписывает входной `.d.ets`. Решает место, а не переключатель: объединение деклараций проходит целиком внутри обработчика `buildStart` плагина etsChecker (`rollup-plugin-ets-checker.ts` → `serviceChecker` в `ets_checker.ts`), а списки входных файлов для es2abc целиком формируются на `buildEnd`; это разные фазы.

Следствие для планирования прямое: сейчас объединение деклараций вынесено за рамки требования, и войдёт ли оно в него, **зависит от того, включён ли `bundledDeclare` в базовом проекте**, а не от формы упаковки HAR. Это значение ещё никто не измерял; оно вынесено в решения, нужные до начала работы.

**Цепочка вызовов от входа записана здесь же, чтобы никому не пришлось искать её заново и разведочная задача не начиналась с нуля.** Вход — `performDeclarationMerging` в `ets_checker.ts`: она сначала берёт `oh-exports` из `oh-package.json5` в корне модуля, а если там пусто — поле `main` с расширением, заменённым на `.d.<исходное расширение>`, вычисляет набор входных файлов и затем вызывает `DeclarationMerger.mergeDeclarationFiles` в `declaration_merger.ts`. Основная цепочка последней: `mergeEntry` → `collectExports` → `collectTypeDependencies` → `resolveNames` → `emit`; она строит собственную вторую Program (`noEmit: true` и пустой `host.writeFile`), а для разрешения модулей использует `createDeclarationModuleResolver` в `declaration_merger_utils.ts` (свой собственный резолвер, не переиспользующий резолвер основной Program); самопроверка вывода — в `validateOutput` в том же файле; имя сопутствующего файла на стыке расширений — в `DeclarationMerger.getCompanionFileName` (вид `<имя входа>-declarations.d.ts` / `.d.ets`); ветка системных API вынесена отдельно в `declaration_merger_sysapi.ts`. Результат объединения записывается обратно в `originalDeclarationContent` таблицы `harFilesRecord` — иначе говоря, оно встраивается в таблицу записей из 1.6 и само на диск не пишет.

## 2. Что нужно сделать

### 2.1 Поддержать объявления аннотаций и их свойства в файлах деклараций

Поддержать попадание объявлений `@interface` и их свойств в `.d.ets`, с дословным сохранением значений по умолчанию у свойств и с выводом типа из значения по умолчанию для свойств без явно указанного типа.

**О чём этот пункт.** Пример из 1.3 должен работать; это соответствует строкам 1–7 таблицы в 1.8: оба вида должны попадать в таблицу диспетчеризации генерации деклараций; свойства аннотаций должны идти путём «передать инициализатор дальше», а не «очистить инициализатор»; `ensureType` должен узнавать оба вида и при отсутствии объявленного типа переходить к вычислению от инициализатора; списки разрешённых для операторов верхнего уровня и для членов должны их пропускать; отсечение по видимости и база сериализации должны их включать.

На стороне tsgo это ложится в `internal/transformers/declarations/transform.go` (аналоги таблицы диспетчеризации и `ensureType`) и `internal/transformers/declarations/util.go` (`isDeclarationAndNotVisible`, `isEnclosingDeclaration`, `canProduceDiagnostics`).

**Есть две ловушки, которых нужно избежать вместе.** Во-первых, список разрешённых и таблица диспетчеризации должны меняться вместе: добавить объявления аннотаций в `isPreservedDeclarationStatement` без соответствующей ветки в `transformTopLevelDeclaration` — значит просто обменять падение в печати вывода на падение на этапе преобразования. Во-вторых, этот пункт в tsgo блокируется проверкой типов: сейчас объявления аннотаций в tsgo связываются как Class, `isArkTSClassLike` в `internal/ast/arkts.go` покрывает только Struct, и сочетание `@interface` с `@Anno class` в проверке типов падает; у `getDeclarationSpaces` в `internal/checker/checker.go` нет соответствующей ветки, и на последней строке происходит паника. Это две предпосылки; без их решения пункт приёмку не пройдёт.

Сценарии:
- Экспортированные объявления аннотаций попадают в `.d.ets`, неэкспортированные — нет
- Свойства аннотаций со значением по умолчанию сохраняют его дословно (включая скобки и операторные формы)
- У свойств аннотаций без типа тип выводится из значения по умолчанию
- Генерация идёт как обычно, когда значение по умолчанию не является константным выражением (сообщается TS28034)
- Объявления аннотаций внутри пространства имён с `declare`

### 2.2 Поддержать сохранение декораторов по списку разрешённых `ets.emitDecorators`

Поддержать выбор декораторов, остающихся в файлах деклараций, по настройке `ets.emitDecorators`, сокращая вызовы с аргументами до голых имён для записей с `emitParameters: false`; а также стирание виртуальных параметров типа в контекстах `@Styles`.

**О чём этот пункт.** См. 1.4; это соответствует строкам 8–10 таблицы в 1.8. Это единственная часть требования, которая «уже сегодня ошибка и не зависит ни от каких предпосылок»: не нужны ни аннотации, ни структуры, ни правки связывания — обычные классы и функции в `.ets` уже её задевают, и её подкрепляют 12 готовых эталонных выводов.

На стороне tsgo правка — в `ensureModifiers` в `internal/transformers/declarations/transform.go`, который сегодня безусловно отсекает все декораторы.

**Учтите, что этот механизм общий с направлением ArkUI.** Движок принадлежит этому требованию, но потребители у него сегодня — сплошь декораторы интерфейса (`@Component` / `@State` / `@Styles` / `@Observed` и подобные). Проверяйте его по критерию «этот путь работает»; не берите заодно на себя семантику декораторов интерфейса.

Сценарии:
- Декораторы из списка разрешённых без аргументов остаются как есть
- Декораторы из списка разрешённых с `emitParameters: false` и аргументами сокращаются до голых имён
- Декораторы, которых нет в списке разрешённых, выбрасываются
- Когда `ets.emitDecorators` не настроена, выбрасывается всё
- Функции и методы с декоратором `@Styles` в файлах деклараций не несут параметров типа

### 2.3 Поддержать сохранение `@Sendable` как есть в файлах деклараций

Поддержать дословный перенос в `.d.ets` декораторов у псевдонимов типов и объявлений функций с `@Sendable`, минуя фильтрацию по списку разрешённых.

**О чём этот пункт.** Эталон открывает для `@Sendable` отдельный путь: на ветках TypeAlias и FunctionDeclaration в `transformTopLevelDeclaration` в `declarations.ts`, как только сработает `isSendableFunctionOrType` в `ohApi.ts`, напрямую выполняется `clean.illegalDecorators = input.illegalDecorators`, **без** фильтрации через `getAnnotationsFromIllegalDecorators`. Сама проверка строгая: узел должен быть объявлением функции или псевдонимом типа, находиться в файле `.ets`, иметь в `illegalDecorators` **ровно одну** запись, и имя это должно быть ровно `Sendable`. Лишний декоратор — и этот путь не берётся.

В исходниках базового проекта `@Sendable` не встречается ни разу, но `@Sendable` входит в зону ответственности команды, и его путь в файлы деклараций идёт параллельно аннотациям из 2.1; без него в поверхности типов, которую получает потребитель, не будет этой отметки.

Сценарии:
- Псевдоним `type` с декоратором `@Sendable` попадает в файл деклараций вместе с декоратором
- То же для объявления `function` с `@Sendable`
- Если у объявления больше одного декоратора, этот путь не берётся и происходит возврат к фильтрации по списку разрешённых

### 2.4 Поддержать отсечение деклараций по видимости и проверку видимости ссылок на аннотации

Поддержать то, чтобы неэкспортированные объявления аннотаций не попадали в `.d.ets`, и чтобы для каждой ссылки на аннотацию в `.d.ets` выполнялась проверка видимости имени сущности.

**О чём этот пункт.** Файл деклараций не должен ссылаться на имя, которого потребитель не видит, иначе при компиляции он получит «не удаётся найти этот тип». В оригинальном TypeScript уже есть полный механизм `checkEntityNameVisibility` для ссылок на типы; эталон распространяет его на аннотации: `checkAnnotationVisibilityByDecorator` в `declarations.ts` проверяет и вызываемую часть `@Anno({...})`, и инициализаторы членов объектного литерала — 18 мест вызова. Вторая половина — добавить случай объявления аннотации в `isDeclarationAndNotVisible`.

На стороне tsgo нужные примитивы уже есть в `internal/transformers/declarations/transform.go`; не хватает подключения ArkTS. Две соответствующие функции — `isDeclarationAndNotVisible` и `isEnclosingDeclaration` в `internal/transformers/declarations/util.go`. Нужны и три места в `transformers/declarations/diagnostics.ts` (единственные изменения ArkTS в этом файле): они включают свойства аннотаций в вычисление привязки для диагностик деклараций.

Сценарии:
- Неэкспортированные объявления аннотаций не появляются в `.d.ets`
- `.d.ets` ссылается на неэкспортированную аннотацию → выдаётся диагностика видимости
- Объектный литерал в аргументе аннотации ссылается на неэкспортированное имя → то же самое
- Применённые аннотации на каждой ветке генерации деклараций выбираются и привязываются заново (в эталоне 20 вызовов `getAnnotations` / `getAnnotationsFromIllegalDecorators` в `declarations.ts`; 2 из них в ветке структуры — вне рамок)

### 2.5 Поддержать удаление `export` внутри пространств имён с `declare` при сохранении декораторов и аннотаций

Поддержать удаление модификаторов `export` у членов внутри пространств имён с `declare` в файлах деклараций с сохранением декораторов и аннотаций ETS.

**О чём этот пункт.** Члены пространства имён с `declare` экспортируются неявно, поэтому оригинальный TypeScript снимает `export`. Эталон при снятии должен вернуть декораторы на место, для чего у него есть отдельный вариант — `stripExportModifiersForEts` в `declarations.ts`: для `ClassDeclaration` он использует `ensureEtsDecorators + getAnnotations`, а для `VariableStatement` — `getAnnotationsFromIllegalDecorators`. В tsgo сегодня есть только вариант, который декораторы не сохраняет, в `internal/transformers/declarations/transform.go`.

Как выглядит вывод, показано на примере `functionAndClassWithDecorator.d.ets` в конце 1.4.

Сценарии:
- У классов внутри пространства имён с `declare` снимается `export`, а декораторы и аннотации сохраняются
- То же для функций внутри пространства имён с `declare`
- Объявления переменных внутри пространства имён с `declare` сохраняют свои аннотации
- `export import` и `export default` не снимаются (в эталоне для них сделано явное исключение)

### 2.6 Поддержать три исправления формы вывода файлов деклараций

Поддержать исключение записей под `oh_modules` при генерации тройных ссылок в `.d.ts`, запись ссылок на типы между пакетами ohpm как переносимых спецификаторов и вывод голой ссылки на тип вместо `import("…").Resource` для типа `Resource` из SDK.

**О чём этот пункт.** Ни одно из трёх не про «урезание исходника»; они меняют форму вывода, поэтому собраны вместе и соответствуют строкам 16–18 таблицы в 1.8.

О тройных ссылках: файл деклараций автоматически несёт набор `/// <reference path="…" />`. Оригинальный TypeScript уже выбрасывает такие ссылки под `node_modules` (потому что после установки пакетов пути ненадёжны), а эталон добавляет то же самое для `oh_modules` в `mapReferencesIntoArray` в `declarations.ts`.

**Важнее всего пункт про переносимый спецификатор.** Когда `symbolToTypeNode` в `checker.ts` сериализует тип, указывающий в другой файл, он сначала строит спецификатор, а затем проверяет его: если внутри есть `/node_modules/`, это «относительный путь, ныряющий в каталог пакета», то есть непереносимый, и спецификатор строится заново в другом режиме — как голое имя пакета. Эталон распространяет эту проверку на ohpm (через `isOhpmAndOhModules` в `ohApi.ts`). Одноимённый `symbolToTypeNode` в `internal/checker/nodebuilderimpl.go` в tsgo жёстко зашивает `/node_modules/` в двух местах и ветки для ohpm не имеет.

Если этого не сделать, пострадает внешняя поверхность типов библиотеки: межпакетный `import("…")` в `.d.ets` запишется относительным или даже абсолютным путём, ныряющим в `oh_modules`; раскладка каталогов у проекта-потребителя другая, чем у издателя, поэтому такой путь никуда не ведёт — **и при этом сборка модуля-издателя не выдаёт ни одной диагностики**.

Сама проверка — одна строка, но чтобы она сработала, лежащий в основе генератор, который «выводит спецификатор обратно из пути к файлу», тоже должен понимать `oh_modules`. На стороне эталона эта часть — в `moduleSpecifiers.ts`, и в ней четыре содержательных куска: `getAllModulePathsWorker` по типу менеджера пакетов решает, «лежит ли этот путь внутри каталога пакета»; `getNearestAncestorDirectoryWithPackageJson` по типу выбирает имя файла манифеста и поднимается вверх до корня пакета; `getNodeModulePathParts` меняет фрагмент-разделитель, по которому путь разбивается на «корень пакета / имя пакета / путь внутри пакета», на `/oh_modules/`; `tryDirectoryWithPackageJson` читает манифест в корне пакета. Аналог в tsgo — `internal/modulespecifiers`. Этот механизм — то же самое, что «научить компилятор понимать каталог пакетов `oh_modules` и манифест `oh-package.json5`» (та же опция `packageManagerType`, те же помощники из `ohApi.ts`), поэтому принадлежность нужно определить один раз; см. 4. Так или иначе, этот пункт отвечает за подключение проверки и её подтверждение при сравнении вывода.

Пункт про `Resource` новый: когда спецификатор модуля заканчивается на `/ets/api/global/resource` или `/ets/dynamic/api/global/resource`, а последний элемент в цепочке символов называется `Resource`, выводится голая ссылка на тип `Resource` вместо `import("…").Resource`. В той же функции он стоит рядом с предыдущим пунктом.

Сценарии:
- В тройных ссылках `.d.ts` нет путей с `oh_modules`
- Ссылки на типы между пакетами ohpm записываются в `.d.ets` голыми именами пакетов, а не относительными путями
- Спецификаторы остаются переносимыми, когда файл приходит через символическую ссылку
- В выводе деклараций, ссылающемся на тип `Resource` из SDK, стоит голая ссылка `Resource`

### 2.7 Поддержать выбор набора вывода и пути публикации по форме модуля

Поддержать определение «какие файлы производить» по форме модуля, выбор относительной базы и корня вывода из трёх путей (общий HSP, HAR с байт-кодом, HAR с исходниками), а также воспроизведение исключения каталога пакетов и правил пути `buildInHar`.

**О чём этот пункт.** См. таблицу набора вывода в 1.5 и таблицу путей в 1.6. На стороне эталона это три функции: ветка по форме в `generateModuleAbc` в `generate_module_abc.ts` (HAR с исходниками здесь делает ранний `return`, пропуская всю генерацию abc) и вычисление путей в `generateSourceFilesInHar` и `genTemporaryPath` в `utils.ts`. Работа — добавить этот слой в tsgo: он читает форму модуля и каталоги, переданные системой сборки, и решает, куда пойдёт каждый вывод; файлы под `oh_modules` по умолчанию исключаются целиком, а при включённом `bundledDeclare` — включаются.

**Не пытайтесь построить этот слой из `outDir` / `declarationDir`.** Эти две опции выражают перенос всего дерева от одной базы, тогда как в эталоне база — одна из трёх в зависимости от формы, а на линии `compileHar && !byteCodeHar` одновременно живут две базы. Насильно свести одно к другому не даст ошибок; оно даст вывод не в том месте — потребитель его не найдёт, а шаг компиляции не подаст ни малейшего сигнала.

Сценарии:
- HAR с исходниками не производит abc — только вывод исходников, декларации и карты исходников
- Общий HSP: попадает в `etsFortgz`, база — корень проекта
- HAR с байт-кодом: попадает в `etsFortgz`, база — корень модуля
- HAR с исходниками: попадает в каталог кэша, база — корень модуля
- Файлы под каталогом пакетов (`oh_modules`) исключаются, а при включённом `bundledDeclare` включаются
- Когда действует `buildInHar`, префикс с именем модуля стирается, а уровень `TEMPORARY` не добавляется

### 2.8 Поддержать сбор и учёт вывода деклараций и две точки записи

Поддержать вынос готовых `.d.ets` / `.d.ts` целиком, повторную генерацию `.ets` / `.ts` в декларации по одному файлу, регистрацию их в таблице записей о выводе и запись на диск через одну из двух точек в зависимости от режима конвейера.

**О чём этот пункт.** На стороне эталона это четыре функции: сбор в `processHarSourceFiles` в `ets_checker.ts`, таблица записей как `harFilesRecord` и `GeneratedFileInHar` в `utils.ts`, и запись через `writeDeclarationFiles` в `ark_utils.ts` (при включённом `singleFileEmit`, вызывается из `beforeBuildEnd` в `rollup-plugin-gen-abc.ts`) и `mangleDeclarationFileName` (при выключенном `singleFileEmit`, вызывается из `handlePostObfuscationTasks` в `ob_config_resolver.ts`, независимо от переключателя обфускации). Подробности в 1.6.

Таблица записей — не внутренняя деталь реализации: объединение деклараций опирается на неё, записывая обратно результаты слияния, обфускация — чтобы найти вывод деклараций, и обе точки записи её обходят. На стороне tsgo нужна равноценная структура данных и её жизненный цикл (когда записи регистрируются, какая точка записи их пишет, как они сбрасываются при инкрементальной сборке).

«Какие файлы выносятся» — само по себе правило: множество обхода — это «разрешённые модули ∪ корневые файлы», то есть достижимость по экспортам плюс транзитивное замыкание импортов, а набор корневых файлов для сборки библиотеки определяется полем `oh-exports` в манифесте пакета. Логика разбора `oh-exports` на стороне tsgo уже написана, но `internal/module/resolver.go` сейчас жёстко подставляет nil, поэтому канал данных не подключён — это требование нужно там как набор корневых файлов, а разрешению модулей — чтобы сообщать «этого файла нет в списке экспорта пакета»; оба применения ждут одного и того же места, и легко выйдет так, что за него не возьмётся никто.

Сценарии:
- Готовые `.d.ets` / `.d.ts` копируются целиком
- `.ets` / `.ts` генерируются по одному файлу в `.d.ets` / `.d.ts` с `forceDtsEmit` (производить даже при ошибке)
- Неудачная генерация одного файла молча пропускается и не прерывает весь прогон (поведение эталона, повторить)
- Декларации записываются и при включённом, и при выключенном `singleFileEmit`
- При включённом `bundledDeclare` регистрация означает немедленную запись
- Набор корневых файлов определяется `oh-exports`, с запасным вариантом — полем `main` в манифесте

### 2.9 Поддержать выбор расширения вывода исходников по `useTsHar` и его попадание в HAR

Поддержать то, что вывод исходников HAR с исходниками остаётся `.ts` или становится `.js` по `useTsHar`, и его регистрацию в таблице записей о выводе.

**О чём этот пункт.** См. абзац про `useTsHar` в 1.5. То, как получается **текст** вывода исходников, в требование не входит; этот пункт отвечает за две вещи: расширение выбирается по `useTsHar` (в эталоне — в `setIncrementalFileInHar` в `rollup-plugin-ets-typescript.ts`); и место назначения регистрируется в `sourceCachePath` таблицы `harFilesRecord` — в живом конвейере на rollup это делает `writeObfuscatedSourceCode` в `ark_utils.ts`, а не `generateSourceFilesInHar`.

**Осторожно: у этого пункта есть обратная зависимость.** Два места на стороне сборки читают это состояние обратно: `getOrCreateLanguageService` в `ets_checker.ts` считает изменение `useTsHar` условием сброса всего кэша при `compileHar && !byteCodeHar`; `process_ui_syntax.ts` предупреждает о классах с `@Sendable` в JS-HAR. Ошибётесь с расширением — сломается не только сам вывод.

Сценарии:
- `useTsHar` выключен: HAR с исходниками производит `.js`
- `useTsHar` включён: HAR с исходниками производит `.ts`
- В обоих случаях место назначения регистрируется в `sourceCachePath` таблицы записей о выводе
- В HAR с исходниками изменение `useTsHar` сбрасывает весь кэш

### 2.10 Поддержать диагностики деклараций при сборке библиотек

Поддержать вычисление и выдачу диагностик деклараций только при сборке библиотек, с пропуском самих файлов деклараций, файлов `.js` и файлов под `oh_modules`.

**О чём этот пункт.** Диагностики деклараций (пачка TS4xxx, «выведенный тип ссылается на невидимое имя») имеют смысл, только когда декларации действительно производятся. Эталон вешает их на ветку `compileHar || compileShared`: `processBuildHap` в `ets_checker.ts` вызывает `printDeclarationDiagnostics` в том же файле, а та явно пропускает эти три вида файлов.

У этого пункта есть стык с направлением «выравнивание поведения диагностик»: какую диагностику убрать, а какую понизить в важности — вопрос того направления; этот пункт владеет только условием «когда вычислять и для каких файлов».

Сценарии:
- При сборке HAP диагностик деклараций нет
- При сборке HAR / HSP они вычисляются, пропуская `.d.ets` / `.d.ts` / `.js` и файлы под `oh_modules`

## 3. Вне рамок

Шесть вещей выглядят как работа над файлами деклараций, но у всех уже есть хозяева; не решайте их заново. «Другие» здесь — не другие документы, а несколько направлений работ, идущих параллельно: направление ArkUI (семантика структур и декораторов интерфейса), сторона вывода скриптов (промежуточный вывод `.js` / abc и стирание аннотаций), направление «научить компилятор понимать `oh_modules`» (каталоги пакетов, манифесты, диагностики видимости), направление выравнивания поведения диагностик, а также обфускация и упаковка. У каждого пункта ниже сказано, к какому направлению он относится.

**Генерация `.d.ets` для структур относится к направлению ArkUI.** Место в эталоне — ветка `StructDeclaration` в `transformTopLevelDeclaration` в `declarations.ts` (члены пропускают виртуальный конструктор, наследование отбрасывается целиком). Это напрямую влияет на приёмку требования; см. 5. Ещё предостережение: в основной ветке tsgo виртуальный конструктор не синтезируется, если явный уже есть, поэтому копирование «обходить начиная с индекса 1» удалит собственный конструктор пользователя; вместо этого нужно фильтровать по `ast.NodeIsVirtual`. Оставьте это тому, кто возьмёт структуры, и не делайте попутно в этом требовании.

**Стирание и вычисление аннотаций в промежуточном выводе `.js` и abc — отдельное направление работ (сторона вывода скриптов).** Граница ясна: всё, что идёт через `getAnnotationPropertyEvaluatedInitializer` / `getAnnotationPropertyInferredType` в `EmitResolver`, относится туда; генерация деклараций читает исходные узлы AST, и общего пути у сторон нет. То же касается стирания аннотаций в `transformers/ts.ts`, `classFields.ts` и `legacyDecorators.ts`.

**Объединение деклараций (declmerge) сейчас вне рамок требования.** Но его условие запуска дважды называли неверно (см. 1.7); настоящее условие — один переключатель `bundledDeclare`. На базовом проекте это значение никто не измерял; если оно окажется включённым, весь этот блок (около 2932 строк, 117 тестовых примеров) возвращается в требование.

**Две вещи, связанные с обфускацией, не делаются:** интерфейс обфускации имён файлов деклараций (`tryMangleFileName` в `ark_utils.ts`) и генерация настройки обфускации для потребителя при публикации HAR. В рамках приёмки обфускация выключена. Заметьте: «стоит включить обфускацию» — и требование снова растёт, а tsgo должен будет отдать обфускатору полный набор файлов программы и карту зависимостей по каждому файлу; сегодня за это никто не отвечает. Ещё напоминание: хотя в имени `mangleDeclarationFileName` есть «mangle», она обязана работать и при выключенной обфускации (это одна из двух точек записи из 1.6); не отрезайте её заодно с «обфускацией».

**Решения о видимости по `oh-exports` во время разрешения модулей относятся к направлению «научить компилятор понимать `oh_modules`».** Это требование использует `oh-exports` только как вход для «какие корневые файлы выносить» и не отвечает за цепочку диагностик «разрешённый файл, которого нет в списке экспорта, — ошибка, и он не попадает в граф модулей».

**Упаковка HAR, подпись и установка после записи вывода остаются за hvigor.** Точка выхода этого требования — «каждый файл, который должен быть произведён, произведён и записан куда надо»; архивация в неё не входит.

## 4. Решения, нужные до начала работы

**Включён ли `bundledDeclare` в базовом проекте на самом деле.** От этого зависит, входит ли в рамки требования объединение деклараций (около 2932 строк, 117 тестовых примеров), и это самая крупная неопределённость требования. Решающее значение — фактическая настройка `arkOptions.bundle.bundledDeclare` в `build-profile.json5`; измерьте её, когда будет зафиксирован снимок базового проекта. Пока ответа нет, реализация держит проверку, которая громко падает: прочитав `bundledDeclare === true`, завершиться с диагностикой, а не молча считать это выключенным — молча считать выключенным значит, что библиотека собирается как обычно и декларации производятся как обычно, но это декларации по файлам, а не единая слитая поверхность типов, и всплывёт это только в проекте-потребителе.

**В какой форме производятся эти 8 HAR.** От этого зависит, какие наборы вывода из 1.5 и какие из трёх путей из 1.6 действительно задействованы на базовом проекте, и, если объединение деклараций срабатывает, что служит ему каталогом входных данных — `declaredFilesPath` или `cachePath/<moduleName>`. Два поля выглядят похоже, но означают не одно и то же, и при выводах их легко перепутать:

- `buildOption.arkOptions.byteCodeHar` — переключатель **на стороне производителя**, он говорит, «в какой форме собирается сам этот модуль». При проектной настройке `useNormalizedOHMUrl: true` отсутствие значения означает HAR с байт-кодом; для HAR с исходниками нужно явно написать `false`.
- `byteCodeHarInfo` — таблица **на стороне потребителя**, она говорит, «какие из пакетов, от которых я завишу, были установлены как архивы `.har`». Критерий — форма зависимости, а не «собирали ли этот HAR мы сами»: решающее доказательство в том, что `getHarData` в `parseUserIntents.ts` выводит корень пакета из `abcPath` через `split('ets')[0]`, а затем дописывает `src/main/resources/...`, — такое выведение пути верно только для распакованного архива `.har`, но не для каталога `build/` локального модуля. Зависимости базового проекта — все каталоги с исходниками `file:../../<mod>`, поэтому таблица пуста (`{}`), — но это **нельзя** читать в обратную сторону, чтобы узнать, в какой форме собираются те 8 модулей.

Этому требованию нужно первое, и его фактическое значение никто не измерял. Решающее измерение: после чистой сборки посмотреть `loader.json` и то, есть ли в cachePath каждого модуля `filesInfo.txt`, и попадает ли вывод деклараций в `etsFortgz` или в каталог кэша. Это не мешает начать с 2.1–2.6.

**Значения переключателей `useTsHar` и `singleFileEmit` на базовом проекте.** Первый решает, что выдаёт HAR с исходниками, `.js` или `.ts` (всё решение из 2.9); второй решает, какой точкой записи пользуются декларации (две ветки в 2.8). Оба передаёт вниз система сборки, и ни один не измерен; измерьте их вместе с предыдущим пунктом при фиксации снимка. Реализовать придётся обе ветки в любом случае — но планированию нужно знать, какую из них базовый проект берёт на самом деле.

**Кто пишет вывод деклараций на диск.** Два варианта: tsgo пишет сразу в конечные каталоги либо tsgo пишет только в кэш, а система сборки копирует в loader_out. Девять входных данных в 1.6 сейчас перечислены под первый вариант (`harOutDir` и `declarationOutDir` задаются отдельно). Пока это не решено, у пункта 2.7 нет входных данных.

**Кому принадлежит механизм построения спецификаторов.** Второй пункт из 2.6 зависит от того, понимает ли `internal/modulespecifiers` каталог `oh_modules`, а этот механизм (четыре функции в `moduleSpecifiers.ts`) — то же самое, что «научить компилятор понимать каталог пакетов `oh_modules` и манифест `oh-package.json5`»: та же опция `packageManagerType`, те же помощники из `ohApi.ts`. Тому, кто вносит в tsgo разрешение модулей с `oh_modules`, удобнее всего сделать и эту часть; это требование отвечает за подключение проверки в `symbolToTypeNode` и её подтверждение при сравнении вывода. **Худший исход — если за неё не возьмётся ни та, ни другая сторона**, потому что при ошибке шаг компиляции не выдаёт ни одной диагностики.

**Кто займётся местом под `oh-exports`.** Логика разбора на стороне tsgo готова, но `internal/module/resolver.go` жёстко подставляет nil, и канал данных не подключён. Применений два: требованию он нужен как набор корневых файлов (2.8), а разрешению модулей — чтобы сообщать «этого файла нет в списке экспорта пакета». Оба применения ждут одного места, и легко выйдет так, что за него не возьмётся никто.

**Браться ли за семейство `@Retention` / `SourceRetention`.** В эталоне есть набор проверок (`isRetentionAnnotationDeclaration`, `checkSourceRetentionAnnotation`, `hasSourceRetentionPolicy` в `checker.ts`), решающих, нужно ли стирать конкретную аннотацию из `.js` и `.d.ets`. Половина ложится в генерацию деклараций (это требование), половина — в логику проверки доступности API SDK; принадлежность не определена.

**Вывод типа свойства аннотации зависит от проверки типов; как планировать предпосылки.** «Вывести тип из значения по умолчанию» из 2.1 в конечном счёте ложится на `createTypeOfExpression`, а проверка типов в tsgo сейчас падает на аннотациях (см. два места в конце 2.1). Решить нужно, относятся эти две предпосылки к данному требованию или к «научить проверку типов понимать объявления аннотаций» — последнее само по себе отдельная работа.

**Механизм эталонных выводов для приёмки по тексту вывода.** Сегодня сравнительные тесты tsgo сравнивают только AST, таблицы символов и диагностики, но не текст вывода, а всё, по чему принимается это требование, — именно текст вывода. Эту стоимость инфраструктуры нужно явно заложить в план, иначе ревью застрянет здесь.

## 5. Приёмка

1. 12 эталонных выводов деклараций (`_submodules/third_party_typescript/tests/dets/`, исходники в `cases/`, ожидаемый вывод в `baselines/reference/*.d.ets`) совпадают байт в байт.
2. Объявления аннотаций совпадают с 9 готовыми выводами эталона (`tests/cases/conformance/annotations/annotationDeclarationFieldInitializer1..8` и `annotationDeclarationFieldInitializerError1`; ожидаемый вывод — разделы `.d.ets` в `tests/baselines/reference/*.js`).
3. Набор вывода и раскладка каталогов для каждой формы модуля совпадают с существующей цепочкой инструментов: собрать один и тот же модуль один раз существующей цепочкой, другой раз tsgo и сравнить наборы путей к файлам в обоих каталогах вывода; затем отдать получившуюся библиотеку в проект-потребитель и собрать его один раз — без диагностик разрешения.

Четыре внешних предпосылки нужно назвать прямо.

**Чтобы заработал критерий 1, сначала нужно перенести эту настройку `ets`.** В `tests/dets/tsconfig.json` для тех 12 примеров лежит: `declaration: true` + `emitDeclarationOnly: true`, 19 записей `emitDecorators` (все с `emitParameters: false`, включая `Entry` / `Component` / `State` / `Styles` / `Builder` / `Observed` и другие), 4 `propertyDecorators`, метод и декоратор `render`, около 100 `components`, полное соответствие `extend.components`, `styles`, `customComponent: "CustomComponent"`, `syntaxComponents`, а также `target: es2021` / `module: commonjs`. Без переноса этой настройки пункт 2.2 — «единственный пункт поставки, который можно начать сразу и у которого есть эталонные выводы» — проверить нельзя.

**10 из 12 эталонных выводов критерия 1 содержат структуры, поэтому приёмка упрётся в направление ArkUI.** Если считать по файлам, только `functionWithDecorators.d.ets` и `functionAndClassWithDecorator.d.ets` полностью свободны от структур; в остальных 10 слово `struct` встречается от 1 до 17 раз (больше всего в `statusManagementOfPageLevelVariables.d.ets`). Иначе говоря, из критерия 1 этим требованием определяются только те 2; остальные 10 должны ждать, пока появится генерация деклараций для структур. Есть два способа это обойти; выберите один до начала работы: разделить критерий 1 на «2 проверяются сразу, 10 — вместе со структурами» либо вынести независимые от структур различия из тех 10 в собственные тестовые примеры этого требования. Не пишите огульное «12 эталонных выводов проходят», чтобы потом на интеграции обнаружить, что проверить их нельзя.

**Эти 12 эталонных выводов сегодня не запускает никакой прогонщик.** Собственные тесты OH на mocha их не запускают (точка входа `src/testRunner/unittests/tsc/etsTests.ts` не импортируется из `tests.ts`, а сама она запускает `lib/tsc.js` отдельным процессом), и на стороне tsgo их тоже никто не потребляет — ни одно из 12 имён примеров не находится ни в `testdata/`, ни в `internal/` этого репозитория. Подключить их придётся с нуля, а в их настройке явно указан внешний файл SDK `interface/sdk-js/api/@internal/component/ets/index-full.d.ts` (на этой машине он есть); эту зависимость тоже нужно либо обработать, либо вырезать из тестового примера.

**9 ожидаемых выводов для критерия 2 хорошего качества и годятся напрямую.** Это собственные примеры OH TSC на соответствие; разделы `.d.ets` лежат внутри эталонных файлов `.js` и покрывают унарные, бинарные, сравнительные и логические операторы, ссылки на идентификаторы, члены `const enum`, литералы массивов и вложенных массивов, а также ошибочную форму «значение по умолчанию не константное выражение». Сопутствующие диагностики — TS28033 и TS28034, и обеих сегодня в tsgo нет.

И последнее: оно в требование не входит, но будет им задето. Как только `ensureModifiers` начнёт сохранять декораторы, эталонные выводы, затрагивающие `.ets` в `testdata/baselines/reference/`, разойдутся массово. По правилам репозитория такое расхождение нужно объяснить по категориям, прежде чем принимать; не ограничивайтесь запуском `baseline-accept`.
