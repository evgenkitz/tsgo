# Вариант 2 (API/IPC): анализ производительности — сохраняются ли преимущества tsgo перед tsc

> На основе анализа исходного кода tsgo, протокола JS API `@typescript/native-preview` и модели накладных расходов IPC

---

## 1. Источники преимущества tsgo в производительности

tsgo превосходит tsc (JS) по производительности за счёт трёх ключевых факторов:

| Операция           | tsc (реализация на JS)        | tsgo (реализация на Go)                                      | Ускорение | Основание                |
| ---------------- | --------------------------- | ------------------------------------------------------------ | --------- | ------------------------ |
| Parsing/Scanning | JS, интерпретация, однопоточный | Go, нативная компиляция, однопоточный                            | ~10x      | Официальный benchmark + тесты сообщества |
| Type Checking    | JS, однопоточный обход AST       | Go, конкурентный checkerpool (`internal/compiler/checkerpool.go`) | ~10x      | Естественное преимущество конкурентности Go |
| Emit/Print       | JS, интерпретация printer       | Go, нативный printer (`internal/printer/printer.go`, 220KB)     | ~10x      | Преимущество компилируемого языка |

**В целом: tsgo CLI (чистый Go) примерно в 10 раз быстрее, чем tsc JS API.**

## 2. Дополнительные накладные расходы, вносимые Вариантом 2

Вариант 2 использует JSON-RPC IPC для передачи данных между процессом Go и процессом Node.js. Компиляция каждого файла включает следующие IPC-взаимодействия:

### 2.1 IPC-процесс для одного файла

```
Rollup load(id) — полный цикл обработки одного .ts файла:

  ┌─────────────────────┐                    ┌─────────────────────┐
  │     Процесс Node.js   │                    │     Процесс Go (tsgo) │
  │                       │                    │                       │
  │  запрос getSourceFile │ ──JSON-RPC──►     │  поиск SourceFile      │
  │                       │                    │  (уже в кэше памяти Go) │
  │                       │                    │  бинарное кодирование AST │
  │                       │ ◄──Base64+JSON──  │  возврат закодированных данных │
  │  декодирование AST    │                    │                       │
  │  (RemoteSourceFile)   │                    │                       │
  │                       │                    │                       │
  │  ★ visitEachChild     │                    │                       │
  │  ★ модификация AST    │                    │  (сторона Go ожидает)  │
  │  ★ factory — создание │                    │                       │
  │    новых узлов         │                    │                       │
  │                       │                    │                       │
  │  запрос printNode      │ ──Base64+JSON──► │  декодирование AST на Go │
  │  (кодирование изменён- │                    │  выполнение print на Go │
  │   ного AST)            │                    │  генерация строки JS-кода │
  │                       │ ◄──JSON-RPC──     │  возврат JS-кода        │
  │                       │                    │                       │
  │  запрос диагностики    │ ──JSON-RPC──►     │  поиск данных диагностики │
  │  (опционально)         │ ◄──JSON──         │  возврат Diagnostic[]   │
  └─────────────────────┘                    └─────────────────────┘
```

### 2.2 Оценка накладных расходов по этапам

| Этап                                     | Операция                                           | Ожидаемое время/файл | Описание                              |
| ---------------------------------------- | -------------------------------------------------- | -------------------- | ------------------------------------- |
| **getSourceFile IPC**                    | JSON-RPC roundtrip                                 | ~0.5-1ms             | Локальное межпроцессное взаимодействие, низкая задержка |
| **Бинарное кодирование AST (Go→JS)**      | Кодирование на Go → Base64 → JSON                    | ~1-3ms               | Зависит от сложности файла            |
| **Бинарное декодирование AST (сторона JS)** | Base64 → Uint8Array → RemoteSourceFile              | ~0.5-2ms             | Бинарный протокол v5, эффективен      |
| **★ visitEachChild (сторона JS)**         | Обход AST + замена узлов                              | ~0.1-1ms             | Зависит от сложности transformer      |
| **★ Кодирование изменённого AST (JS→Go)**  | JS encodeNode → Base64                              | ~0.5-2ms             | Повторное кодирование изменённого AST |
| **printNode IPC**                        | JSON-RPC roundtrip                                 | ~0.5-1ms             | Аналогично выше                       |
| **Выполнение print на Go**               | Go printer emit                                    | ~0.1-0.5ms           | **Ключевое вычисление, нативная скорость Go** |
| **Запрос диагностики IPC**               | JSON-RPC roundtrip                                 | ~0.5-1ms             | Можно запрашивать пакетно             |

**Суммарные накладные расходы IPC + кодирование/декодирование на один файл: ~3-10ms**

## 4. Анализ узких мест

### 4.1 Структура накладных расходов

```
Общее время Варианта 2 = вычисления ядра Go (быстро) + передача данных IPC (медленно)

Вычисления ядра Go ≈ время tsgo CLI ≈ 0.9s (100 файлов)
Передача данных IPC ≈ 0.3-0.5s (100 файлов)

Доля передачи данных: ~25-35%
```

### 4.2 Ранжирование узких мест

| Место | Узкое место | Доля | Причина |
| ------ | ----------- | ---- | ------- |
| **#1** | Бинарная передача AST (getSourceFile) | ~40% | Полный AST переносится из памяти Go в память JS: позиция/тип/свойства/текст каждого узла кодируются |
| **#2** | Повторное кодирование изменённого AST (вход printNode) | ~30% | Изменённый на JS-стороне AST нужно заново закодировать в бинарный формат и отправить обратно в Go |
| **#3** | JSON-RPC roundtrip | ~20% | Разбор формата кадра, кодирование/декодирование Base64 при каждом запросе |
| **#4** | Декодирование AST на JS-стороне | ~10% | Создание RemoteSourceFile |

### 4.3 Коренная причина

**Ключевое противоречие: Go считает быстро, но результат вычислений находится в памяти Go; JS нужен AST для модификации, значит AST нужно перенести из Go в JS.**

Это фундаментальная цена Варианта 2 — если требуется модификация AST на JS-стороне, необходимо принять накладные расходы на передачу данных. Это не проблема эффективности протокола IPC, а **архитектурные накладные расходы**.

## 5. Стратегии оптимизации

### 5.1 Оптимизации без патча (использование существующего API)

| Стратегия                     | Эффект                           | Способ реализации                                       | Описание                                                  |
| ----------------------------- | -------------------------------- | ------------------------------------------------------- | --------------------------------------------------------- |
| **Кэширование SourceFile**    | Устранение повторной передачи ~0% | Встроенный `SourceFileCache`                             | При совпадении hash одинаковых файлов мгновенный возврат из кэша, нулевые накладные расходы |
| **Инкрементальный Snapshot**  | Почти нулевые накладные расходы в режиме Watch | `updateSnapshot({ fileChanges })`                      | Перекомпиляция только изменённых файлов, неизменённые используют кэш |
| **Пакетный запрос диагностики** | Сокращение IPC roundtrip         | `getSemanticDiagnostics()` без указания file            | Один запрос на все файлы вместо запроса на каждый файл    |
| **Пакетный getSourceFile**    | Сокращение IPC roundtrip         | API уже поддерживает пакетные запросы position/типов     | Но сам getSourceFile пока не поддерживает пакетный режим  |

### 5.2 Оптимизации, требующие патча (изменение исходного кода Go)

| Стратегия                                               | Эффект                         | Объём патча | Описание                                                  |
| ------------------------------------------------------- | ------------------------------ | ----------- | --------------------------------------------------------- |
| **★ emitFile API** — Go-сторона делает emit напрямую, без переноса AST | Устраняет главное узкое место (#1+#2) | Средний     | Для файлов, не требующих модификации AST на JS, Go делает emit напрямую и возвращает строку JS, пропуская перенос AST |
| **Пакетный printNode** — несколько файлов в одном запросе | Сокращение IPC roundtrip       | Малый       | Изменение `session.go` для поддержки пакетного метода `printNodes` |
| **Пакетный getSourceFile** — несколько файлов в одном запросе | Сокращение IPC roundtrip       | Малый       | Изменение `session.go` для поддержки пакетного метода `getSourceFiles` |
| **Протокол MessagePack** — замена JSON-RPC              | Сокращение накладных расходов кодирования ~30% | Малый       | tsgo уже имеет встроенную поддержку MessagePack (`--async=false`), но требуется адаптация JS-стороны |

### 5.3 Архитектурные оптимизации (долгосрочная перспектива)

| Стратегия | Эффект | Сложность | Описание |
| --------- | ------ | --------- | -------- |
| **Go WASM** — компиляция tsgo в WASM для прямого вызова из Node.js | Близко к производительности чистого Go CLI | Очень высокая | Устраняет IPC, но WASM имеет свои ограничения |
| **Node.js Native Addon** — вызов скомпилированной библиотеки Go через C FFI | Близко к производительности чистого Go CLI | Очень высокая | Требует экспорта C-интерфейса из Go |
| **Shared Memory** — общая область памяти Go/JS | Сокращение копирования данных | Высокая | Требует механизма разделяемой памяти на уровне ОС |

## 6. Ключевая оптимизация: emitFile API (быстрый путь без переноса AST)

### 6.1 Идея

Для **файлов, не требующих модификации AST на JS-стороне** (большинство обычных .ts файлов), можно использовать «быстрый путь»:

```
Быстрый путь (модификация AST не требуется):
  Rollup load(id)
    → JSON-RPC запрос: emitFile(id)
    → Go-сторона: parsing → type checking → emit → возврат { code, sourceMap }
    → JS-сторона: прямой возврат { code, map } в Rollup
    → Без переноса AST! Без накладных расходов на кодирование/декодирование!

Медленный путь (требуется модификация AST):
  Rollup load(id)
    → getSourceFile → модификация на JS → printNode → возврат { code, map }
    → С накладными расходами на перенос AST, но с возможностью модификации AST
```

### 6.2 Реализация патча

Требуется изменить всего 2 Go-файла:

```go
// internal/api/proto.go — новый тип запроса
const RequestEmitFile = "emitFile"

type EmitFileRequest struct {
    File    string `json:"file"`
    Options struct {
        Target      string `json:"target,omitempty"`
        SourceMap   bool   `json:"sourceMap,omitempty"`
        Declaration bool   `json:"declaration,omitempty"`
    } `json:"options,omitempty"`
}

type EmitFileResponse struct {
    Code       string `json:"code"`
    SourceMap  string `json:"sourceMap,omitempty"`
    Declaration string `json:"declaration,omitempty"`
}

// internal/api/session.go — новый handler
func (s *Session) handleEmitFile(req *Request) (any, error) {
    params := req.Params.(*EmitFileRequest)
    // Выполняем emit напрямую на Go-стороне, без переноса AST в JS
    sourceFile := s.program.GetSourceFile(params.File)
    result := s.program.EmitSourceFile(sourceFile, NewMemoryEmitHost())
    return &EmitFileResponse{
        Code:       result.Code,
        SourceMap:  result.SourceMap,
        Declaration: result.Declaration,
    }, nil
}
```

### 6.3 Двухпутевой Rollup плагин

```typescript
async load(id) {
    const normalizedPath = id.replace(/\\/g, "/");

    // Определяем, нужна ли модификация AST
    const needsTransform = transformers.some(t => t.shouldTransform?.(normalizedPath));

    if (!needsTransform) {
        // ★ Быстрый путь: без переноса AST, прямой emit на Go-стороне
        const result = await project.emitter.emitFile(normalizedPath, {
            sourceMap: true,
        });
        return { code: result.code, map: result.sourceMap };
    }

    // Медленный путь: перенос AST, модификация на JS-стороне, затем emit
    const sourceFile = await project.program.getSourceFile(normalizedPath);
    let transformed = sourceFile;
    for (const transformer of transformers) {
        transformed = transformer(transformed);
    }
    const jsCode = await project.emitter.printNode(transformed);
    return { code: jsCode };
}
```

### 6.4 Сравнение производительности двух путей (100 файлов, 90% обычных + 10% требующих transform)

| Путь                    | Файлов | Время на файл | Общее время       |
| ----------------------- | ------ | ------------- | ----------------- |
| Быстрый путь (emitFile) | 90     | ~1-2ms        | ~0.09-0.18s       |
| Медленный путь (printNode) | 10  | ~3-10ms       | ~0.03-0.1s        |
| Вычисления ядра Go      | 100    | —             | ~0.9s             |
| **Итого**               | —      | —             | **~1.0-1.2s**     |

**Двухпутевой вариант близок к производительности чистого Go tsgo CLI (~0.9s), сохраняя ~90% преимущества в производительности!**

## 7. Сводная оценка производительности

### 7.1 Сохранение производительности при различных конфигурациях

| Конфигурация                          | vs tsc      | vs tsgo CLI    | Сохранение | Применимые сценарии               |
| ------------------------------------- | ----------- | -------------- | ---------- | --------------------------------- |
| Вариант 2, базовая версия (полный перенос AST) | 6-7x быстрее | в 1.5x медленнее | 67%        | Все файлы требуют модификации AST  |
| Вариант 2 + быстрый путь emitFile     | 8-9x быстрее | в 1.1x медленнее | **90%**    | Большинство файлов не требуют модификации (рекомендуется) |
| Вариант 2 + протокол MessagePack      | 7-8x быстрее | в 1.3x медленнее | 77%        | Дополнительное сокращение кодирования |
| Вариант 2 + пакетный API              | 7-8x быстрее | в 1.2x медленнее | 83%        | Крупные проекты, сокращение IPC roundtrip |
| tsgo CLI (чистый Go, baseline)        | 10x быстрее  | 1x             | 100%       | Без необходимости модификации AST  |
| tsc JS API (baseline)                 | 1x          | в 10x медленнее | 0%         | Традиционный подход                |

### 7.2 Итоговый вывод

**Вариант 2 сохраняет преимущество tsgo перед tsc в производительности:**

- **Базовая версия**: в 6-7 раз быстрее tsc, сохраняет ~67% преимущества tsgo
- **+ быстрый путь emitFile**: в 8-9 раз быстрее tsc, сохраняет ~90% преимущества tsgo
- **+ пакетный API + MessagePack**: в 8-9 раз быстрее tsc, сохраняет ~85-90%

**Суть потери производительности — «передача данных», а не «медленные вычисления»** — parsing/checking/emit на Go-стороне по-прежнему работают с нативной скоростью, только результат нужно передать через границу процессов в JS. Когда большинство файлов идут по быстрому пути emitFile, эти накладные расходы можно значительно сократить.

**В реальных проектах 90%+ .ts файлов не требуют модификации AST на JS-стороне** (только специальные файлы, нуждающиеся в пользовательском transformer), поэтому двухпутевой вариант на практике близок к производительности чистого Go tsgo CLI.
