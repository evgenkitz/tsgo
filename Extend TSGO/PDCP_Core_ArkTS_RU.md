## 1. Поддержка атомарных возможностей

### 1.1 Проблема: зачем нужна атомарность

Текущий OH TSC представляет собой **чёрный ящик**: ace_ets2bundle может только вызывать `ts.createProgram`, запускающий полную компиляцию, без возможности выполнить только разбор, только проверку или только линтинг. Это приводит к следующему:

```
Текущее состояние (режим чёрного ящика):

  ace_ets2bundle                     TSC
  ┌────────────┐         ┌──────────────────────┐
  │ Требуется: │         │                      │
  │ только     │──полная─│→ Scanner → Parser    │
  │ parse      │ компи-  │    → Binder → Checker│
  │            │ ляция   │      → Linter → Emit │
  │ Требуется: │         │                      │
  │ только     │──полная─│→                     │
  │ lint       │ компи-  │                      │
  │            │ ляция   │                      │
  │ Требуется: │         │                      │
  │ только     │──полная─│→                     │
  │ check      │ компи-  │                      │
  └────────────┘ ляция   └──────────────────────┘

  → Каждый запрос прогоняет полный конвейер — масса бесполезных вычислений
  → В сценарии IDE достаточно parse + check, но принудительно выполняются lint + emit
  → В сборочном конвейере etsChecker и do_arkTS_linter — это два независимых полных вызова
```

### 1.2 Решение: матрица атомарных возможностей tsgo

Архитектура tsgo естественным образом поддерживает обрыв конвейера — каждый этап является независимой функцией, и выполнение можно остановить на любом из них:

```
Атомарные возможности tsgo (CLI + внутренний API):

  ┌─────────────────────────────────────────────────────────────────┐
  │                      Конвейер компиляции tsgo                    │
  │                                                                 │
  │  ┌────────┐  ┌────────┐  ┌────────┐  ┌────────┐  ┌─────────┐    │
  │  │Scanner │─→│Parser  │─→│Binder  │─→│Checker │─→│Emitter  │    │
  │  │        │  │        │  │        │  │        │  │         │    │
  │  └────────┘  └────────┘  └────────┘  │ +встро- │  │         │   │
  │                                      │ енный   │  │         │   │
  │                                      │ Linter  │  │         │   │
  │                                      └────────┘  └─────────┘    │
  │                                                                 │
  │  Атомарная                                                       │
  │  возможность ①     ②          ③          ④           ⑤         │
  │  ───────────────────────────────────────────────────────────── │
  │                                                                 │
  │  ① parse-only    выдаёт только AST + синтаксические диагностики  │
  │  ② bind-only     выдаёт AST + таблицу символов + области видимости│
  │  ③ check-only    выдаёт AST + диагностики типов (вкл. Linter)   │
  │  ④ lint-only     выдаёт AST + диагностики по 92 правилам ArkTS  │
  │  ⑤ full-emit     выдаёт .js + .d.ets + SourceMap                │
  └─────────────────────────────────────────────────────────────────┘
```

### 1.4 Способ реализации

**На уровне CLI**:

```
Дизайн CLI для атомарных возможностей tsgo:

  # ① Только разбор (выдаёт AST, без проверок)
  tsgo --option parseOnly -p project/

  # ③ Только проверка типов (включая встроенный Linter, без emit)
  tsgo --noEmit --option lintOnly -p project/

  # ④ Только ArkTS Lint (пропускает стандартную проверку типов, только 92 правила)
  tsgo --noEmit --option strictCheckerOnly -p project/

  # ⑤ Полная компиляция (эквивалент текущего поведения tsc)
  tsgo -p project/
```

**На уровне Go API** (долгосрочная перспектива, для вызова после перехода ace_ets2bundle на Go):

```go
// Пример атомарного API

// ① parse-only
ast, diagnostics := tsgo.ParseFiles(ctx, fileNames, options)

// ③ check-only (включая встроенный Linter)
program := tsgo.NewProgram(ctx, host)
diagnostics := program.GetSemanticDiagnostics(file)  // включает ArkTS Linter

// ④ lint-only (пропускает стандартную проверку TS, только правила ArkTS)
program := tsgo.NewProgram(ctx, host, tsgo.StrictCheckerOnly(true))
diagnostics := program.GetArkTSDiagnostics(file)
```

## 2. Консолидация Transform Node — устранение узкого места межпроцессного взаимодействия Node.js ↔ tsgo

### 2.1 Проблема: что фактически делает текущий Emit

В сборочном конвейере OH «emit» — это не просто кодогенерация. Плагин `etsTransform` в составе ace_ets2bundle выполняет большое количество преобразований AST:

```
Объём работы Transform в текущем ace_ets2bundle:

  ace_ets2bundle (Node.js)                        TSC (тот же процесс Node.js)
  ┌─────────────────────────┐                    ┌───────────────────┐
  │ Плагин etsTransform:    │                    │                   │
  │                         │                    │  ts.factory.*     │
  │ ① Развёртывание         │ ──100+ вызовов──→  │  (фабрика узлов   │
  │   компонентов ArkUI     │                    │   AST)            │
  │   Column(){...} →       │                    │                   │
  │   __JSX({...})          │                    │  ts.transform()   │
  │                         │ ──преобр. AST──→   │  (конвейер        │
  │ ② Внедрение управления  │                    │   преобразований) │
  │   состоянием            │                    │                   │
  │   @State → __Observed   │                    │  ts.createPrinter │
  │                         │ ──кодогенерация─→  │  (AST→текст JS)   │
  │ ③ Развёртывание         │                    │                   │
  │   декораторов           │                    │                   │
  │   @Component →          │                    │                   │
  │   __registerComponent   │                    │                   │
  │                         │                    │                   │
  │ ④ Преобразование        │                    │                   │
  │   условного рендеринга  │                    │                   │
  │   if(true){A()} →       │                    │                   │
  │   __condRender(A)       │                    │                   │
  └─────────────────────────┘                    └───────────────────┘

  Так как TSC работает в том же процессе Node.js, эти вызовы передаются
  как указатели на память — накладные расходы ≈ 0
```

**Ключевая проблема**: как только tsgo заменит TSC, вызовы `ts.factory.*` превратятся в **межпроцессные операции**:

```
Узкое место после миграции (если Transform останется на стороне Node.js):

  ace_ets2bundle (Node.js)                     tsgo (процесс Go)
  ┌─────────────────────────┐                ┌───────────────────┐
  │ Плагин etsTransform:    │                │                   │
  │                         │  сериализация  │ tsgo может только │
  │ ① Требует узлы AST      │ ──AST JSON──→  │ выдать текст .js  │
  │ ② Требует ts.factory    │ ←──AST JSON──  │ Не может передать │
  │ ③ Требует конвейер      │  десериализация│ Go-объекты в      │
  │    transform             │                │ Node.js           │
  │ ④ Требует createPrinter │                │                   │
  │                         │                │                   │
  │  При каждом вызове:     │                │                   │
  │  ┌──────────────────┐   │                │                   │
  │  │ Go-объект→JSON   │   │  ← узкое место!│                   │
  │  │ IPC-передача~10ms│   │     крупный     │                   │
  │  │ JSON→JS-объект   │   │     проект:     │                   │
  │  │ = ~30ms на вызов │   │     100+ вызовов│                   │
  │  └──────────────────┘   │     ×30ms = 3с  │                   │
  └─────────────────────────┘                └───────────────────┘

  → 100+ вызовов ts.factory × межпроцессная передача ≈ 3–10 с доп. затрат
  → Полностью сводит на нет преимущество tsgo в скорости компиляции
```

### 2.2 Решение: консолидация Transform Node в процессе tsgo

**Основная идея**: перенести логику Transform, завязанную на `ts.factory.*`, из ace_ets2bundle внутрь tsgo, чтобы tsgo выдавал окончательный .js, а стороне Node.js не требовалось выполнять AST-преобразования.

```
Целевая архитектура (Transform консолидирован в tsgo):

  ace_ets2bundle (Node.js)                  tsgo (процесс Go)
  ┌─────────────────────────┐              ┌───────────────────────┐
  │ Плагин etsChecker:      │              │                       │
  │                         │  вызов CLI   │  Scanner → Parser     │
  │ tsgo -p project/        │─────────────→│       → Binder        │
  │                         │              │       → Checker       │
  │ Только читает выходные  │              │       → Transform     │ ← новый
  │ файлы:                  │              │       → Emitter       │
  │ .js + .d.ets + .abc     │              │                       │
  │                         │←──────────── │  Выдаёт: готовый .js  │
  │ Больше не делает        │  файловая    │                       │
  │ AST-преобразований!     │  система     │                       │
  └─────────────────────────┘              └───────────────────────┘

  Роль ace_ets2bundle меняется с «манипулятора AST» на «потребителя результата»
  → Нулевое межпроцессное взаимодействие по AST
  → Transform внутри tsgo — это операции с указателями на память, накладные расходы ≈ 0
```

  │   │   checkEtsComponent(node)         ← arktscomponents  │      │
  │   └─────────────────────────────────────────────────────┘      │
  │                │                                                │
  │                ↓                                                │
  │   Объединённый вывод всех диагностик                            │
  │   (стандартные TS + правила ArkTS)                              │
  │   → Одна проверка — полный результат                            │
  │   → Устранение последовательной цепочки «сначала check,         │
  │     потом lint» из OH TSC                                       │
  └─────────────────────────────────────────────────────────────────┘
```

### 3.5 Гарантия согласованности результатов: многоуровневый конвейер верификации

«Согласованность» — это не «прогнать один раз и на глаз прикинуть, что похоже». Требуется **воспроизводимый, количественно измеримый, регрессионно-защищённый** механизм верификации. Ниже — конкретная схема.

#### 3.5.1 Определение согласованности

Прежде чем обсуждать «согласованность», определим, что считать «согласованным», а что — «допустимым ожидаемым расхождением»:

```
┌───────────────────────────────────────────────────────────────────┐
│                  Критерии оценки согласованности                     │
│                                                                   │
│  ┌─────────────────────────────────────────────────────────────┐ │
│  │ Жёсткие требования (обязательное совпадение)                 │ │
│  │                                                              │ │
│  │  • Полное совпадение идентификаторов FaultID                 │ │
│  │    OH выдаёт ARKTS_1060505 → tsgo обязан выдать ARKTS_1060505│ │
│  │                                                              │ │
│  │  • Эквивалентность условий срабатывания                      │ │
│  │    На одном и том же коде: где OH сообщает об ошибке,        │ │
│  │    там же должен сообщить tsgo, и наоборот                   │ │
│  │    То есть: ложных срабатываний = 0%, пропусков = 0%         │ │
│  │                                                              │ │
│  │  • Совпадение уровня серьёзности диагностики                 │ │
│  │    OH: error → tsgo не может выдать warning                  │ │
│  └─────────────────────────────────────────────────────────────┘ │
│                                                                   │
│  ┌─────────────────────────────────────────────────────────────┐ │
│  │ Допустимые расхождения (фиксируются, но не блокируют)        │ │
│  │                                                              │ │
│  │  • Различие в номерах строк/столбцов                         │ │
│  │    OH TSC использует смещение UTF-16, tsgo — UTF-8           │ │
│  │    → Требуется преобразование UTF-16↔UTF-8 перед сравнением  │ │
│  │    → После преобразования возможно расхождение на 1 столбец  │ │
│  │      из-за различий в обработке символов перевода строки —   │ │
│  │      считается нормальным                                    │ │
│  │                                                              │ │
│  │  • Различие в формулировках диагностических сообщений        │ │
│  │    Совпадают по сути, но различаются wording                 │ │
│  │    (напр., «not allowed» vs «prohibited»)                    │ │
│  │    → Требуется ручная проверка семантической эквивалентности, │ │
│  │      фиксируется, но не блокирует                             │ │
│  │                                                              │ │
│  │  • Дополнительные или отсутствующие диагностики из-за        │ │
│  │    различий систем типов TS 4.9 → 7.0                        │ │
│  │    tsgo основан на TS 7.0 — вывод типов строже/слабее        │ │
│  │    → Требуется поштучный анализ, является ли расхождение      │ │
│  │      обоснованным отличием вышестоящей версии                 │ │
│  │    → Фиксируется в реестре расхождений, решение принимает     │ │
│  │      человек                                                 │ │
│  └─────────────────────────────────────────────────────────────┘ │
└───────────────────────────────────────────────────────────────────┘
```

#### 3.5.3 Трудозатраты на верификацию согласованности

| Этап | Содержание | Трудозатраты |
|------|-----------|--------------|
| Подготовка тестовых наборов | Извлечение из репозитория OH TSC + преобразование формата | 2 чел.-дня |
| Разработка скрипта сравнения | Нормализация JSON + преобразование UTF-16↔UTF-8 + автоматизация CI | 3 чел.-дня |
| Верификация Phase A (30 правил) | Поправильное сравнение + разбор расхождений | 3 чел.-дня |
| Верификация Phase B (62 правила) | Поправильное сравнение + разбор расхождений + граничные случаи Sendable | 5 чел.-дней |
| Текущее регрессионное сопровождение | Перезапуск после каждого rebase tsgo | 0,5 чел.-дня / раз |

#### 3.6.3 Корректная формулировка показателей производительности

При наличии базовых данных показатели производительности должны формулироваться как **кратность относительно baseline**, а не как абсолютные проценты:

  «check-only — не более 50%»           «Цель tsgo check-only:
   ← 50% от чего? Нет точки отсчёта     ≤ X% от tsc_full_compile_ms
                                         из baseline-отчёта.
                                         X определяется после
                                         построения baseline»

  «Память unified checker — не более     «Цель unified checker tsgo:
   40%»                                  ≤ Y% от tsc + linter_peak_rss_mb
   ← 40% от чего? Нет точки отсчёта      из baseline-отчёта.
                                         Y определяется после
                                         построения baseline»

  То есть: сначала baseline → затем целевые значения на основе
  baseline → затем проверка достижения целей
```

## 6. Риски и меры по снижению

| Риск | Критичность | Вероятность | Меры по снижению |
|------|------------|-------------|-----------------|
| Логика Transform расходится с текущим поведением ace_ets2bundle | Высокая | Средняя | Этап 1 — без миграции Transform; Этап 2 — поправильное сравнение через .js diff |
| Вывод диагностик после миграции 92 правил расходится с OH TSC | Высокая | Средняя | Автоматическое выявление через многоуровневый конвейер верификации (раздел 3.5) + ручное решение |
| Фреймворк grammarchecks не поддерживает сложные проверки, требуемые некоторыми правилами Linter | Средняя | Низкая | Расширение фреймворка или добавление вспомогательных функций |
| Вызовы ts.factory в ace_ets2bundle несовместимы со структурой AST tsgo | Высокая | Средняя | Этап 1 — сохранить сторону JS без изменений; Этап 2 — постепенная миграция |
| Правила Sendable требуют API потокового анализа checker — tsgo может не поддерживать | Средняя | Средняя | Предварительная проверка покрытия API потокового анализа в tsgo |
| Сложность получения базовых проектов (нет подходящих проектов OH с открытым кодом) | Средняя | Средняя | Скомбинировать примеры из официального репозитория OH Samples или сконструировать покрывающий проект вручную |
| Различия систем типов TS 4.9→7.0 приводят к неустранимым конфликтам правил | Средняя | Средняя | Фиксация в реестре расхождений, совместное решение архитектора и команды OH |

## 7. Критерии успеха

### 7.1 Функциональные критерии (не зависят от baseline, проверяются немедленно)

| Измерение | Критерий | Способ проверки |
|-----------|---------|-----------------|
| **Атомарность** | tsgo поддерживает четыре режима: `--parseOnly` / `--checkOnly` / `--lintOnly` / fullEmit по умолчанию | Проверка аргументов CLI + корректность вывода каждого режима |
| **Transform — Этап 1** | ace_ets2bundle после замены пути к бинарному файлу tsc корректно собирает примеры проектов OH | Полная компиляция трёх базовых проектов S/M/L проходит успешно |
| **Transform — Этап 2** | tsgo самостоятельно выполняет развёртывание компонентов ArkUI, внедрение управления состоянием, развёртывание декораторов | Сравнение diff вывода .js между OH TSC + etsTransform и tsgo |
| **Унифицированная проверка** | 92/92 правил проходят конвейер верификации согласованности (см. раздел 3.5) | Скрипт автоматизированного сравнения + реестр решений о расхождениях |

### 7.2 Критерии производительности (целевые значения определяются после построения baseline)

Показатели производительности **не задаются заранее в абсолютных числах**, а определяются по следующей процедуре:

```
┌────────────────────────────────────────────────────────────────┐
│            Процедура определения критериев производительности      │
│                                                                │
│  Шаг 1: Базовые измерения                                      │
│  ├── Прогнать OH TSC на трёх проектах S/M/L, зафиксировать:    │
│  │   • Время полной компиляции                                  │
│  │   • Время только Lint (tsc + runArkTSLinter)                │
│  │   • Время инкрементальной компиляции                         │
│  │   • Пиковое потребление памяти RSS                           │
│  │   → Записать в baseline_report.json                          │
│  │                                                             │
│  Шаг 2: Определение целевых значений                            │
│  ├── На основе базовых данных установить цели tsgo по принципу: │
│  │   • Полная компиляция: цель < время полной компиляции (baseline)│
│  │     (конкретный коэффициент определяется по данным baseline,   │
│  │      начальное ожидание — ускорение ≥ 3×)                     │
│  │   • Только Lint: цель < время Lint (baseline)                 │
│  │     (устранение повторного создания checker + параллелизация) │
│  │   • Инкрементальная компиляция: цель < время инкрем. (baseline)│
│  │   • Пиковая память: цель < пиковая память (baseline)          │
│  │     (устранение копии read-only checker + встроенный Linter)  │
│  │                                                             │
│  Шаг 3: Проверка                                               │
│  ├── После завершения реализации tsgo перепрогнать S/M/L        │
│  │   в той же среде                                             │
│  ├── Результаты записать в поля tsgo_* файла baseline_report.json│
│  └── Сравнить с целевыми значениями из Шага 2, определить       │
│      достижение/недостижение                                     │
│                                                                │
│  Вывод:                                                        │
│  ┌─────────────┬──────────┬──────────┬────────┬──────────┐   │
│  │ Проект       │ Baseline │ tsgo     │ Цель   │ Достигну-│   │
│  │ (масштаб)    │ (tsc)    │ фактич.  │        │ та цель? │   │
│  ├─────────────┼──────────┼──────────┼────────┼──────────┤   │
│  │ S полная (ms)│ baseline │  факт    │ <baseline│ ✓/✗    │   │
│  │ M полная (ms)│ baseline │  факт    │ <baseline│ ✓/✗    │   │
│  │ L полная (ms)│ baseline │  факт    │ <baseline│ ✓/✗    │   │
│  │ ...         │   ...    │   ...    │  ...   │  ...     │   │
│  └─────────────┴──────────┴──────────┴────────┴──────────┘   │
└────────────────────────────────────────────────────────────────┘
```

### 7.3 Предварительные условия

Перед проверкой критериев производительности должны быть выполнены следующие предварительные условия:

| Предварительное условие | Статус | Примечание |
|-------------------------|--------|-----------|
| Выбор базовых проектов | Ожидает выполнения | Требуется выбрать три проекта S/M/L из проектов OH с открытым кодом или официальных Samples |
| Базовые измерения OH TSC | Ожидает выполнения | Прогнать OH TSC в фиксированной среде, записать baseline_report.json |
| Прохождение проверки согласованности 92 правил | Ожидает выполнения | Сначала гарантировать корректность результатов, затем — производительность |
