tsgo — Инкрементальная система сборкиv2

Как tsc --build и tsc --incremental устроены изнутри. Два уровня: проект-оркестратор + инкрементальная компиляция файлов.

🧩 Два уровня инкрементальности

Система сборки разделена на два независимых, но взаимодействующих пакета:

Уровень 1: Оркестратор проектов

internal/execute/build/

  • Управляет графом проектов (tsconfig → tsconfig)
  • Строит DAG зависимостей через references
  • Определяет, какой проект перекомпилировать
  • Читает/пишет .tsbuildinfo для проверки актуальности
  • Координирует параллельную сборку
  • Watch mode: отслеживает изменения файлов
Уровень 2: Инкрементальная компиляция

internal/execute/incremental/

  • Работает внутри одного проекта (одного tsconfig)
  • Сравнивает снапшоты файлов: что изменилось с прошлого раза
  • Перестраивает только изменившиеся и транзитивно-затронутые файлы
  • Кэширует диагностики и сигнатуры .d.ts
  • Формирует BuildInfo для сохранения в .tsbuildinfo

🏗 Граф проектов: GenerateGraph

Оркестратор получает список tsconfig-файлов из командной строки и строит направленный ациклический граф (DAG) проектов через поле references.

Алгоритм построения:
  1. Для каждого tsconfig создаётся BuildTask
  2. Рекурсивно обходятся references — создаются task'и для подпроектов
  3. DFS по графу для поиска циклов (ошибка, если найден)
  4. Топологическая сортировка — порядок сборки
  5. Каждый task ждёт upstream.done перед стартом
Параллелизм:
  • До 4 параллельных task'ов (настраивается через --builders N)
  • Task запускается, когда все upstream task'и завершены
  • Сигнал завершения — закрытие канала done chan struct{}
  • Результат агрегируется в orchestratorResult

9 Сравнить mtime output-файлов с input (для не-incremental режима)
10 Проверить upstream .d.ts — если они новее наших output, мы устарели
11 Проверить времена tsconfig и extended config'ов

📸 Снапшот (snapshot) — ядро инкрементальной компиляции

Снапшот — это состояние проекта на момент прошлой компиляции. Он хранит всё, что нужно для определения «что изменилось».

Сериализуемые поля (в .tsbuildinfo):
fileInfos На каждый файл: version (xxh3-хэш), signature (хэш .d.ts), affectsGlobalScope, impliedNodeFormat
options CompilerOptions на момент прошлой сборки
referencedMap Для каждого файла — множество файлов, на которые он ссылается (imports, triple-slash refs)
semanticDiagnosticsPerFile Кэш семантических диагностик (для быстрого вывода без перепроверки)
emitDiagnosticsPerFile Кэш диагностик emit'а .d.ts
changedFilesSet Файлы, изменившиеся в последней компиляции
affectedFilesPendingEmit Файлы, требующие emit + какой тип emit'а (JS, d.ts, или оба)
emitSignatures Хэши сгенерированных .d.ts для отслеживания изменений
hasErrors Были ли ошибки (даже с --noCheck)
checkPending Ожидает ли семантическая проверка
latestChangedDtsFile Путь к последнему изменившемуся .d.ts
Не-сериализуемые поля (in-memory only):
buildInfoEmitPending Нужно ли записать .tsbuildinfo (atomic.Bool)
hasChangedDtsFile Изменился ли хоть один .d.ts в этом цикле
hasErrorsFromOldState Были ли ошибки в старом состоянии (для сравнения)
allFilesExcludingDefaultLibraryFile Кэш списка файлов (ленивый, sync.Once)
hasEmitDiagnostics Есть ли диагностики emit'а

💾 .tsbuildinfo — структура файла

Формат: JSON. Имя файла: <tsconfig-name>.tsbuildinfo. Это полный слепок состояния проекта после компиляции.

Где находится файл: 
// Упрощённая логика GetBuildInfoFileName():
// 1. Если задан явно:
if tsBuildInfoFile != "" → использовать его

// 2. Если есть OutDir:
if OutDir != "" && RootDir != "":
  OutDir / relative(RootDir → configBaseName) + ".tsbuildinfo"

// Пример:
//   tsconfig: /src/app/tsconfig.json
//   rootDir:  /src
//   outDir:   /dist
//   → /dist/app/tsconfig.tsbuildinfo

// 3. По умолчанию: рядом с tsconfig
configFileWithoutExtension + ".tsbuildinfo"
//   → /src/app/tsconfig.tsbuildinfo
JSON-схема BuildInfo: 
{
  "version": "6.0.0-dev",          // версия tsgo
  "errors": false,
  "semanticErrors": false,
  "checkPending": false,
  "root": [ [1,5], 7 ],       // ID root-файлов
  "fileNames": ["src/a.ts", ...],
  "fileInfos": [
    { "version": "a1b2c3...",        // xxh3 хэш текста
      "signature": "d4e5f6...",      // хэш .d.ts
      "affectsGlobalScope": false }
  ],
  "referencedMap": [                    // граф импортов
    { "file": 1, "refs": 1 }        // fileId → listId
  ],
  "fileIdsList": [[2,3,5], ...],  // дедупликация
  "options": { ... },                    // CompilerOptions
  "semanticDiagnosticsPerFile": [...],
  "emitDiagnosticsPerFile": [...],
  "changeFileSet": [4],
  "affectedFilesPendingEmit": [...],
  "latestChangedDtsFile": "src/a.ts",
  "emitSignatures": [...],
  "resolvedRoot": [...]
}

🗜 Оптимизации формата

Приём Описание
Числовые fileId Имена файлов хранятся один раз в массиве fileNames[], везде используются числовые ID. Экономит место при повторяющихся ссылках.
Дедупликация списков Списки fileId (например, reference-множества) хранятся в fileIdsList и переиспользуются через индексы.
Run-length кодирование root Последовательные ID: [1, 5] означает «ID с 1 по 5». Одиночный ID — просто число.
Относительные пути Все пути относительно директории .tsbuildinfo. Экономит место и делает файл переносимым.
omitzero Пустые/нулевые поля не сериализуются (тег json:"...,omitzero").
xxh3-хэши 128-битный xxh3 (не криптографический, но быстрый и с низкой вероятностью коллизий).

🗑 Когда кэш инвалидируется

Полная инвалидация (пересборка с нуля):
  • Версия tsgo изменилась (BuildInfo.Version != core.Version())
  • Изменились compilerOptions
  • Изменился набор root-файлов
  • Опция --force
  • Output-файлы отсутствуют
  • Входной файл отсутствует
  • .tsbuildinfo отсутствует или повреждён
Частичная инвалидация:
  • Изменился текст файла (другой xxh3-хэш) → файл в changedFilesSet
  • Изменился .d.ts → транзитивное распространение по графу импортов
  • Изменился globalScope → все файлы затронуты
  • Удалился globally-scoped файл → все файлы затронуты

📊 Статистика: насколько быстрее

Приблизительные оценки для проекта из ~1000 файлов:

Сценарий Без инкрементального режима С инкрементальным режимом Ускорение
Нет изменений (tsc --build) ~15s (полный type-check + emit) < 100ms (проверка хэшей + UpToDate) ~150x
1 файл изменён ~15s ~1-3s (только изменённый файл + затронутые потребители) ~5-15x
Изменился global .d.ts ~15s ~15s (все файлы затронуты — эквивалентно полной сборке) ~1x
Watch mode (250ms цикл) N/A < 10ms на цикл без изменений (только stat + хэши) —
